# Notification admission and negative cases

[Specification index](../../REFERENCE_SPEC.md) · [capture matrix](../reference/02-state-capture.md) · [Android surface ownership](15-android-surface-ownership.md)

An iPhone notification, an ActivityKit Live Activity and a first-party system alert are different sources. Apple describes Live Activities as ongoing progress that goes beyond push notifications; its iOS 27 notification guide describes ordinary notification presentation and Notification Center separately. The iPhone Island guide also mentions **alerts**, so do not infer that every brief Island presentation is an ActivityKit session or that no ordinary alert can ever affect its appearance. Capture the actual surface and source for each case. [Apple Live Activities HIG](https://developer.apple.com/design/human-interface-guidelines/live-activities), [iOS 27 notifications guide](https://support.apple.com/guide/iphone/view-and-respond-to-notifications-iph6534c01bc/27/ios/27), [iOS 27 Island guide](https://support.apple.com/guide/iphone/view-live-activities-in-the-dynamic-island-iph28f50d10d/27/ios/27)

## R26 native boundary capture

Use the controlled publisher to send (a) a standard visible notification, (b) a Time Sensitive notification if its entitlement/settings permit it, (c) a notification with an action, (d) a silent or muted notification, and (e) an ActivityKit Live Activity start/update/alert for the **same task and text**. Repeat unlocked on Home and inside another app, locked, during one existing Island activity and with Focus enabled. Film from before delivery until the display settles. Record banner/Lock Screen/Notification Center versus Island presence, exact onset and dismissal, touch destination, sound/wake, notification settings and whether the underlying Live Activity is still active. Do not turn a missing Island frame into a universal rule without repeatable capture and source logs. [iOS 27 notifications guide](https://support.apple.com/guide/iphone/view-and-respond-to-notifications-iph6534c01bc/27/ios/27), [ActivityKit alerts](https://developer.apple.com/documentation/activitykit/alertconfiguration)

This negative case has a paired Android trial: post an ordinary chat/alert notification, an ongoing notification with no verified task contract, a system-promoted Live Update, and a known app-owned task source. Run each while another Island source is active. A correct result may be **no replica card**. Capture the native shade/card/chip, replica state, listener event, promotion flag and dismissal/teardown separately.

## Android admission rule

Treat the notification listener as a discovery feed, not as automatic Island membership. First pass the [listener visibility gate](27-notification-listener-visibility.md): a missing callback may reflect an API 31+ type filter, policy or disconnection rather than an absent publisher task. A posted notification gives identity and fields; `FLAG_ONGOING_EVENT` only signals an ongoing event, and a `Notification.Action` only supplies a publisher action token. On supported builds, system-set `FLAG_PROMOTED_ONGOING` is stronger evidence that Android actually promoted a Live Update, but it still does not supply Apple's region layout, task identity beyond the published fields, or an iPhone visual verdict. Android explicitly reserves Live Updates for ongoing, user-initiated, time-sensitive activity and excludes chat messages, ads, generic alerts and quick access shortcuts. [Android listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [Android notification](https://developer.android.com/reference/android/app/Notification), [Android Live Updates](https://developer.android.com/develop/ui/views/notifications/live-update)

| Candidate | Admission to replica source store | Rendering consequence |
| --- | --- | --- |
| Direct app-owned active task or real media session | Admit only while its task/session is live, with stable ID and usable published fields. | Eligible for the measured arbiter; action and destination still need their own proof. |
| Actually promoted Android Live Update from an inspected publisher | Candidate for admission after checking package/version, notification key, current fields, user opt-in and source semantics. | Coordinate with the **native chip**; no duplicate tap target or invented action. Demotion and dismissal can change system presentation without proving task end. |
| Ongoing but unpromoted third-party notification | Require a named, tested publisher adapter that establishes a task start/end and truthful field/action mapping. | Otherwise keep it in Android's notification surface. `FLAG_ONGOING_EVENT` alone is insufficient. |
| One-off message, alert, promotion, group summary, redacted or unknown source | Do not infer a Live Activity from text, category, icon, ranking, urgency or repeated posts. | No Island card by default. Preserve native alert, shade and notification tap. |

This admission policy is a **provisional Android product rule**, not a claim that it reproduces Apple's unpublished first-party alert routing. When R26 iPhone footage shows an Island alert outside ActivityKit, add a source-specific Android adapter only if a real corresponding system/publisher event and owner can be proven. Otherwise record the difference as `approximate` or `unsupported` for the selected route. Never suppress another app's native notification or promote it merely to make the replica busy.

When one Android task changes from an ordinary notification to a system-promoted Live Update, preserve its source ID and recorded destination/action tokens. Promotion is a native presentation decision, not a new task; user demotion is not proof the task ended. A publisher can request promotion only for an ongoing, user-initiated, time-sensitive phase, including an imminent phase of a longer task. A task that has not begun stays ordinary until the qualifying phase. [Android Live Update usage](https://developer.android.com/develop/ui/views/notifications/live-update), [surface ownership](15-android-surface-ownership.md).

## Transition and failure proof

For each admitted notification source, film post, update, user demotion, user dismissal, channel disablement, publisher end and listener revocation independently. Preserve the notification key through update. On removal, withdraw that notification-backed card and invalidate its actions immediately, but record the callback reason separately from any independently confirmed task-end event; click, snooze, lockdown, timeout or app cancel need not mean the task ended. A verified media session or cooperating publisher task may continue under its own source record. Readmit only from a fresh post or independent current state, and resnapshot after listener reconnect. Verify that a normal notification from the **same package** does not inherit the active task's slot, token, progress or card. Record the native chip and shade card before and after every change. [Notification listener removal reasons](https://developer.android.com/reference/android/service/notification/NotificationListenerService#onNotificationRemoved(android.service.notification.StatusBarNotification,android.service.notification.NotificationListenerService.RankingMap,int)), [Android Live Update demotion](https://developer.android.com/develop/ui/views/notifications/live-update)

R26 remains `unverified` until native iPhone and target Android footage shows both positive and negative outcomes. A correct absence is a measured result, not a missing screenshot.

For a named third-party app, write the [publisher adapter record](43-third-party-adapter-contract.md) before assigning its notification or media session an Island slot. A notification delegate, second media session, or same-package ordinary alert must not inherit the first task's identity or actions.
