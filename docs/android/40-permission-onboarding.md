# Android permission onboarding and return-state proof

[Specification index](../../REFERENCE_SPEC.md) · [permission inventory](07-android-permissions.md) · [listener visibility](27-notification-listener-visibility.md)

Overlay drawing, notification listening and posting the replica's **own** notifications are separate capabilities. Explain the specific feature before each user-owned Settings step and recheck the actual state after return; a Settings activity result is not a grant. Do not request phone, Bluetooth, microphone, exact-alarm or other feature-specific grants merely to draw the Island. [Android overlay permission](https://developer.android.com/reference/android/Manifest.permission#SYSTEM_ALERT_WINDOW), [notification listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [notification posting permission](https://developer.android.com/develop/ui/views/notifications/notification-permission).

## Locally installed APK gate

Android 17's compatibility definition requires Restricted Settings for apps installed from a local file or downloaded through a non-store app. Its enforced list includes **display over other apps** and **notification listener** access. For a covered installation, confirmation must come from that app's system App Info page before either access can be granted; opening the ordinary overlay/listener Settings screen alone is insufficient. Google documents the user path as Settings → Apps → this app → More → Allow restricted settings, followed by the device's confirmation. The exact wording and screen layout are device-specific. This gate is controlled by installation source and device policy, not by `POST_NOTIFICATIONS`; do not build a silent bypass or imply that every store-installed copy encounters it. [Android 17 compatibility definition: Restricted Settings](https://source.android.com/docs/compatibility/17/android-17-cdd), [Android Help: restricted settings](https://support.google.com/android/answer/12623953).

When a toggle is blocked, show the feature that remains unavailable and let the user decide whether to use App Info. After they return, recheck the restricted-setting outcome **and** the separate overlay/listener grant; for the listener, also wait for `onListenerConnected()` and a fresh snapshot. Do not misdiagnose a blocked grant as an empty publisher feed. An app-owned renderer may still be usable without listener access, while denied overlay access prevents the APK drawing route. Record install source, the system restriction message, App Info confirmation or refusal, Settings grant result and actual runtime behavior as separate facts.

## Device acceptance

For the chosen phone/build, film overlay denied → granted → revoked, listener denied → granted but not connected → connected → filtered → revoked, and own-notification denied → granted. With a disposable test installation, compare a locally installed APK against a trusted-store installation if both are available; do not change the user's production installation to manufacture this comparison. For the local APK, attempt overlay and listener grants before and after the App Info confirmation, including refusal and return without changing a toggle. Record install source, requested Settings action, handler, screen and restriction message, user/profile, confirmation result, separate grant query, service callback, visible overlay/native chip, first source frame and teardown. A permission gate passes only for observed behavior on that build; it does not prove iPhone visual or system-layer parity.
