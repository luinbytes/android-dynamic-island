# Android integration architecture

[Specification index](../../REFERENCE_SPEC.md)

## Android integration architecture gate

| Route | What it can prove | What remains outside its control | Build condition |
| --- | --- | --- | --- |
| Regular APK with `TYPE_APPLICATION_OVERLAY` | Visual engine, gestures and real public-API adapters over ordinary apps; portable installation on phones that grant overlay and listener access. | Status-bar Z-order, system suppression, keyguard/AOD ownership, private Android indicators, and full status-chip coordination. It cannot establish system-layer 1:1 parity. [Window type](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY) | Use as a design and integration prototype, and as a possible final **approximation** if that is the chosen delivery route. |
| Target-specific SystemUI change in an Android OS build | Can place the component in the same system process that owns the status bar and interacts with notification shade, keyguard, AOD, screen decorations, and platform callbacks. This is the route to investigate for native system-layer placement and lifecycle. [AOSP SystemUI README](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/README.md) | Still depends on the chosen phone's cutout and OS implementation, Android event contracts, third-party publisher data, and native iPhone reference measurements. AOSP names are not guaranteed to match an OEM fork. | Requires a supported device/OS source or OEM integration path, compatible build/signing and a safe device test plan; not a universal APK. [AOSP privileged apps](https://source.android.com/docs/core/permissions/perms-allowlist), [signature permissions](https://source.android.com/docs/core/permissions/signature-permission-allowlist) |
| Resource overlay only | Can change existing overlayable SystemUI resources, such as some dimensions or colors. | Cannot add the new event arbitration, interactions or animated Island renderer by itself. [AOSP RRO](https://source.android.com/docs/core/runtime/rros) | Supplementary theming tool only if the selected OS exposes the needed resources. |

**Architecture decision after target selection:** complete the [device qualification gate](18-device-qualification.md) for the phone's exact build, bootloader/build constraints, SystemUI implementation, available source and recovery path. If the user requires system-layer parity, evaluate the SystemUI route on that exact target before declaring a regular APK sufficient. Do not flash, unlock or replace a user's OS as a research step: AOSP documents that bootloader state changes wipe user data. [AOSP device state](https://source.android.com/docs/security/features/verifiedboot/device-state). A SystemUI implementation is a platform component with scoped signal access, not a reason to grant a companion APK every privileged permission.

**Public API refresh:** Android 17 adds Live Update semantic styling and `MetricStyle`, including a critical metric that can inform a status chip. These are publisher notification APIs; the documented chip still has system-owned presentation and a 96 dp maximum width. They improve native task data and appearance within Android's notification contract but do not change the APK/SystemUI route distinction above. Recheck the exact target OS for newer APIs before implementation. [Android 17 features](https://developer.android.com/about/versions/17/features), [MetricStyle](https://developer.android.com/reference/android/app/Notification.MetricStyle), [Live Update chip](https://developer.android.com/develop/ui/views/notifications/live-update).

### SystemUI integration seams to inspect on the selected OS

These are **AOSP research anchors**, not a claim that an OEM build exposes the same classes or that an Island can be inserted at one fixed hook. Find the corresponding owner in the selected build and trace its actual drawing, touch and lifecycle path before changing code. [AOSP SystemUI README](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/README.md).

| Concern | AOSP anchor | Native-feel proof |
| --- | --- | --- |
| Status-bar placement and shade | `CentralSurfaces` coordinates status bar/shade behavior; AOSP also has `StatusBarWindowController` for the status-bar window and `StatusBarContentInsetsProvider` for content bounds across rotations. Inspect all three equivalents in the selected build before choosing the Island's drawing and input owner. [AOSP SystemUI README](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/README.md), [status-bar window controller](https://android.googlesource.com/platform/frameworks/base/+/615ad7a7880964ed28ccfdd6eebaa84342911b1e/packages/SystemUI/src/com/android/systemui/statusbar/window/StatusBarWindowController.java), [content insets provider](https://android.googlesource.com/platform/frameworks/base/+/e5bca37fb55dcf49be7fbe95b01c0e5b02c03997/packages/SystemUI/src/com/android/systemui/statusbar/phone/StatusBarContentInsetsProvider.kt) | Island fits the cutout while clock, status icons, privacy indicators and shade gesture remain usable; window bounds and reserved content space remain correct in each rotation, and notifications are not duplicated. |
| App-window handoff | AOSP's WM Shell participates in window transitions and is hosted with SystemUI; inspect the selected build's app-close, Home/recents and launch transition path before connecting it to the Island renderer. | R1a motion can be synchronized to the actual app transition without a duplicate overlay frame, dropped source content or a stuck Island. An arbitrary publisher may not expose a matching source element. [AOSP WM Shell overview](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/libs/WindowManager/Shell/src/com/android/wm/shell/docs/overview.md) |
| Physical cutout | `ScreenDecorations` can draw software cutout/corner decorations and privacy-dot surfaces; inspect whether the target uses software or hardware composition and who owns the cutout fill. [AOSP ScreenDecorations](https://android.googlesource.com/platform/frameworks/base/+/1685e6b9319b/packages/SystemUI/src/com/android/systemui/ScreenDecorations.java) | The Island mask meets the real camera boundary through rotation and appearance changes without a doubled black edge, hidden privacy dot or exposed sensor pixels. |
| Lock and dim states | `CentralSurfaces` interacts with keyguard/AOD; `KeyguardViewMediator` manages keyguard state. Inspect the selected build's effective notification redaction and profile policy before rendering third-party fields. | The unlocked Island withdraws at lock transition; a separate lock/AOD presentation uses the chosen platform's lifecycle, dimming and per-user visibility rules. No raw listener text leaks on keyguard or AOD. [Notification visibility](https://developer.android.com/reference/android/app/Notification#visibility) |
| Charging screensaver | Android `DreamService` is an interactive screensaver that may run when an idle phone is charging or docked; it is a candidate surface only if the user enables it on the selected device. | A paired R11a run proves whether the chosen phone launches the dream, presents the activity, allows the tap transition and returns cleanly to lock/unlock. It is not automatic iOS StandBy parity. [DreamService](https://developer.android.com/reference/android/service/dreams/DreamService) |
| Privacy indicator and details | AOSP's privacy-indicator flow has SystemUI render camera/microphone/location usage and send taps to `PermissionController` for the usage dialog. | Indicator stays visible and opens the correct app-usage details when the Island is compact, expanded, alerting or switching activities; its animation is not mistaken for a Live Activity. [AOSP privacy indicators](https://source.android.com/docs/core/permissions/privacy-indicators) |
| Screen-recording chip | AOSP has a SystemUI screen-recording chip/interactor path in published source history; find the equivalent in the selected build rather than assuming its current location or behavior. | System recording countdown, active state, stop action and saved/error result have one owner and do not show duplicate chip and Island control. [AOSP screen-record chip change](https://android.googlesource.com/platform/frameworks/base/+/72b3afc154c2987b4e7f56f5b0866b39f737e12a) |
| Search/assistant entry and shade gesture | Android exposes an assistant role, `ACTION_ASSIST` and a global-search intent candidate, but the target OS decides which providers and gesture surfaces are active. Trace its actual SystemUI top-edge gesture, search and assistant launch paths. | R24/R24a Island swipe reaches the selected Search or assistant surface only when supported, while an ordinary shade pull remains usable; report Search and Siri-specific conversation behavior separately. [Assistant role](https://developer.android.com/reference/android/app/role/RoleManager#ROLE_ASSISTANT), [assist intent](https://developer.android.com/reference/android/content/Intent#ACTION_ASSIST), [SearchManager](https://developer.android.com/reference/android/app/SearchManager#INTENT_ACTION_GLOBAL_SEARCH) |
| Biometric and keyguard owner | Trace the selected build's keyguard and biometric-prompt presentation before placing any Island animation near the sensor. The platform owns authentication results. | R25 unlock and own-app authentication keep the real prompt, failure, credential fallback and activity handoff legible; no replica control appears to approve a different app's authentication. [Android BiometricPrompt](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt) |
| Initialization and service lifetime | `SystemUIApplication` builds the dependency graph; current AOSP `CoreStartable` supports an ordered dependency binding, `start()` and `onBootCompleted()`. Inspect the selected build's user/process lifecycle before registering the Island feature. [AOSP CoreStartable](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/src/com/android/systemui/CoreStartable.java) | No startup/locked-boot race, duplicate renderer, cross-user leak or orphaned input surface after SystemUI restart. |

Native placement still needs a single source-of-truth event model. Feed it from platform-owned signals where available and from publisher-defined media/notification contracts where needed; identify the owner of each action, dismissal and priority decision. A SystemUI build should replace the APK overlay renderer, not display both. No selected device, build or source tree exists yet, so every seam above remains an inspection task.
