# Publisher foreground and Island ownership

[Specification index](../../REFERENCE_SPEC.md) · [app handoff](../verification/08-platform-proof-gates.md) · [state machine](../design/14-state-machine.md)

Apple describes a Live Activity appearing in the Dynamic Island while its publisher app is not in use, while other items can appear there when the app is open. Its design session shows one app's content moving into the Island as the user leaves that app. Those statements do **not** specify an exact visibility rule for every publisher, multiple-source arbitration, or the iPhone 18 Pro Max animation. R1b measures those facts separately from R1a's motion. [Apple Live Activities HIG](https://developer.apple.com/design/human-interface-guidelines/live-activities), [Apple design session](https://developer.apple.com/videos/play/wwdc2023/10194/)

## R1b native capture

Use a fixture activity with a visible in-app representation and stable source ID. Start it in the publisher foreground, stay there, leave to Home, open an unrelated app, return by the Island and by the app switcher, then end it while the publisher is foreground. Repeat after process restart and with a **second app's** Live Activity already active. For every interval record publisher foreground/visible state, Island source IDs, contour, content, selection, touch result, first/last frame and whether the task itself remains active. Repeat with an incoming alert and with the app in split or other supported foreground presentation if the chosen OS offers one. Do not infer source termination from temporary Island absence.

## Android ownership by route

| Route | Foreground evidence | Presentation gate |
| --- | --- | --- |
| App-owned task in APK prototype | The publisher can report its own activity lifecycle and stable task state; the renderer can receive an explicit cooperation event if it is a separate app. | Reconcile app foreground with source validity. If the measured iPhone hides or changes that publisher's Island content, suppress only the relevant **presentation**, retaining the real task and allowing other sources to occupy slots. Prove launch/return timing and avoid a duplicate in-app and overlay control. |
| Unrelated third-party publisher in APK prototype | Its media or notification contract does not by itself say whether its UI is foreground. `UsageStatsManager.queryEvents()` can expose app-usage events only with user-granted usage access and is unavailable while locked on current Android versions; it is historical event data, not a shared window-animation clock. [Android UsageStatsManager](https://developer.android.com/reference/android/app/usage/UsageStatsManager), [usage permission](https://developer.android.com/reference/android/Manifest.permission#PACKAGE_USAGE_STATS) | Do not request broad usage access merely to guess a publisher's foreground handoff. Until a target-tested, user-authorized foreground signal or publisher cooperation exists, label this behavior `unverified` or `approximate` and keep the source-specific route explicit. An overlay cannot claim synchronized app-window motion. |
| Target-specific SystemUI implementation | Trace the selected build's actual focused/visible task and WM Shell transition path, with multi-window, shade, keyguard and user/profile changes. [AOSP WM Shell](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/libs/WindowManager/Shell/src/com/android/wm/shell/docs/overview.md), [AOSP SystemUI](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/README.md) | One arbiter decides whether the foreground publisher's card remains, changes or yields to another source. The renderer follows that build's real transition and restores from live source state when the user leaves the app. AOSP anchors are not proof of an OEM hook. |

Foreground ownership is independent of notification promotion. A publisher can keep an active task and an Android notification while its app UI is open; a native Live Update chip may also be present. Record the actual native chip/card, replica visibility and user tap target as separate surfaces. Never cancel the underlying notification simply to match an iPhone foreground frame. [Android Live Updates](https://developer.android.com/develop/ui/views/notifications/live-update), [surface ownership](15-android-surface-ownership.md)

For each transition, log `(source ID, foreground owner, active task state, visible Island IDs, selected ID, native chip state, app-window transition ID, first/last Island frame)`. Compare iPhone and Android results using the [paired protocol](../verification/12-comparison-protocol.md). R1b remains `unverified` until the target devices establish the foreground policy and the route's actual behavior.
