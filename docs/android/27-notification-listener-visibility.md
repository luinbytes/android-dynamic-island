# Notification listener visibility and filters

[Specification index](../../REFERENCE_SPEC.md) · [Android events](06-android-events.md) · [notification admission](20-notification-admission.md)

An enabled `NotificationListenerService` is **not** proof that every third-party notification reaches the replica. Since API 31, Android lets a listener declare default filter types (`ongoing`, `conversations`, `alerting`, `silent`) and types it never wants to receive. An absent default list allows all types by default, but a user override can supersede that default; a present empty list allows none. The ongoing type covers important ongoing notifications above `IMPORTANCE_MIN`. The selected OS can also withhold work-profile notifications under device policy. [Android listener filters and lifecycle](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [Android work-profile policy](https://developer.android.com/work/managed-profiles#listen_for_notifications).

## Implementation contract

| Condition | Replica behavior | Proof before admitting a third-party source |
| --- | --- | --- |
| Listener has not reached `onListenerConnected()` or has received `onListenerDisconnected()` | Mark listener-derived sources unavailable, remove executable actions immediately, and withhold stale cards. After disconnection, only `requestRebind()` is safe until reconnection. | Record connection/disconnection time, reconnection, fresh `getActiveNotifications()` snapshot and first subsequent callback. [Listener lifecycle](https://developer.android.com/reference/android/service/notification/NotificationListenerService) |
| Ongoing/alerting/silent/conversation type filtered by user or manifest | Do not infer that a publisher has no active task merely because its notification is absent. Show a diagnostic reason for missing observation; keep the native notification untouched. | For a controlled publisher, post each type and record native shade presence, listener callback/snapshot presence, channel importance and current filter setting on the exact build. [Filter types](https://developer.android.com/reference/android/service/notification/NotificationListenerService#FLAG_FILTER_TYPE_ONGOING) |
| Publisher notification is in a managed profile | Treat access as policy-conditional. Do not merge personal and work sources or leak work text into another profile's Island. | Post paired personal/work notifications; record user/profile, profile lock, DPC policy, native visibility, callback and replica visibility. [Managed profiles](https://developer.android.com/work/managed-profiles#listen_for_notifications) |
| Listener sees a notification but it is not an admitted task | Apply the separate source-specific admission contract; discovery alone does not authorize a card or action. | Record package, notification key, channel/ranking, supported actions and task identity; prove the admission rule. [Admission contract](20-notification-admission.md) |

`onNotificationRankingUpdate(RankingMap)` is a separate event from `onNotificationPosted`. Apply its **current** map to active notification keys; do not retain a `Ranking` object as live state because Android says rankings do not update in place. `getCurrentRanking()` provides a current snapshot only for active notifications, and the map passed with a post/remove event is usually the relevant snapshot for that event. If a callback, promotion change or process restart leaves the adapter's notification fields or system-chip state uncertain, reconcile from `getActiveNotifications()` after connection and film the native surface before claiming the chip changed. A removed `StatusBarNotification` may be a lightweight object missing heavy fields, so match removal by its stable notification key and previously stored source identity, then invalidate actions immediately; do not rehydrate a removed card from the old ranking. [Android listener callbacks](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [Ranking snapshot contract](https://developer.android.com/reference/android/service/notification/NotificationListenerService.Ranking).

On API 26+, consume the three-argument `onNotificationRemoved(sbn, rankingMap, reason)` and record the reason with the exact `(UserHandle, notification key)`. `REASON_CANCEL`/`REASON_CANCEL_ALL` mean user dismissal of the **notification**; `REASON_CLICK` means the notification was removed after a click; `REASON_APP_CANCEL` may accompany publisher completion or replacement. None of these alone proves the publisher's underlying task ended. `REASON_SNOOZED` can be followed by a later post, and `REASON_LOCKDOWN` requires immediate removal of listener-held private content and actions; Android documents reposting lockdown-removed notifications after lockdown exits. Channel/package bans, profile shutdown and timeout likewise remove observation without supplying a universal task-end event. In every case, invalidate tokens from the removed record and withdraw a card supported only by that notification. Keep a separately confirmed media or publisher task under its own ID, with its own current fields/actions; readmit a repost only from fresh delivered data, not cached text or the removal reason. Record unknown and OEM-specific reasons without inventing semantics. [Removal callback and reasons](https://developer.android.com/reference/android/service/notification/NotificationListenerService#onNotificationRemoved(android.service.notification.StatusBarNotification,android.service.notification.NotificationListenerService.RankingMap,int)).

For an **active** notification on API 31+, also record `Ranking.getLockscreenVisibilityOverride()` beside the publisher's `Notification.visibility` and optional `publicVersion`. The ranking value reports a user or device-policy override, or `VISIBILITY_NO_OVERRIDE`; it is not the fully rendered lock-screen result. Refresh it after ranking callbacks and user/profile changes. A listener may hold full notification fields while SystemUI shows a redacted or absent card on a secure lock screen or during screen sharing; do not reuse the raw listener payload as a public Island view. Test effective native visibility, user lock-screen settings, profile lock and capture output separately. [Ranking visibility override](https://developer.android.com/reference/android/service/notification/NotificationListenerService.Ranking#getLockscreenVisibilityOverride()), [notification visibility](https://developer.android.com/reference/android/app/Notification#visibility).

On Android 15+, detected one-time codes in notifications are withheld from **untrusted** listeners. Screen sharing also hides notification content from remote viewers; where the publisher supplies `publicVersion`, Android can show that replacement, otherwise it redacts the content. The default on-device system recorder is documented as exempt from these screen-share protections, so a saved local recording is not proof of what a remote viewer saw. Treat these as three independently observed outputs: listener payload, physical/native notification, and receiving-side shared image. The replica must not reconstruct an OTP from an old payload, another notification field or a visible native card; an ordinary code alert is not Island task admission anyway. [Android 15 privacy changes](https://developer.android.com/about/versions/15/behavior-changes-all#otp_redaction).

Do not declare `disabled_filter_types` for `ongoing` in an implementation that relies on ongoing publisher notifications. A manifest default is only a starting preference, not a guarantee of user access. Do not use `migrateNotificationFilter()` as a way to override the user's choice; Android documents that migration is ignored after a user-set filter. Keep the user's filter controls in Settings, explain the specific missing source in local diagnostics, and re-evaluate observation after settings return. [Listener filter metadata and migration](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

Observing or passively drawing a notification must not silently mark it viewed or dismiss it. Android's `setNotificationsShown(keys)` reports that the user has viewed those exact notification keys and requires sufficient confidence, such as an explicit display interaction. If a replica explicitly opens the current notification `contentIntent` and the notification carries `FLAG_AUTO_CANCEL`, follow the listener's documented `cancelNotification(key)` click behavior; do not apply that cancellation to expanded-card viewing, source switching or a separate action button. Record the native shade's seen/removal state and callback reason after each path on the target build. [Listener seen/click API](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

## Target-device acceptance

On the named Android build, run a publisher fixture that posts distinct, identified ongoing, alerting, silent and conversation notifications. For each type, compare native notification presence with listener callbacks and `getActiveNotifications()` after connection, then repeat after user filter changes, listener access revocation/restoration, process restart and profile lock/unlock. Change ranking/channel importance while a notification key remains active and record `onNotificationRankingUpdate`, the new map, fresh active-notification fields and actual native presentation; then remove the source during a ranking change and confirm its action is invalidated. Separately trigger click, user dismiss, app cancel/repost, snooze, timeout, channel disablement and lockdown; record the callback reason, native surface, card withdrawal and fresh repost or independent-session continuity. For public/private/secret variants, record publisher visibility, public version, ranking visibility override and the actual locked and screen-shared output for each active key. Include one active media session to verify its independent media adapter and one promoted ongoing notification to compare the system-set promoted flag with actual chip visibility. A filtered or removed notification is **unobserved**, not proof that its underlying task ended. The adapter can only claim reliable coverage for the source types and profiles actually delivered on the chosen build. [Android listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [promoted flag](https://developer.android.com/reference/android/app/Notification#FLAG_PROMOTED_ONGOING).

Add a controlled synthetic-code notification and the same publisher's nonsensitive ongoing task as separate records. Verify the listener's redacted versus delivered fields, native shade, replica admission **or absence**, and remote recipient image without using a real login code. Repeat a public-version notification and one without a public version under a receiving-side screen share and local system recording. Do not infer cross-app data access from the Android 17 SMS OTP delay: that rule governs SMS broadcast/provider access, while this test governs notifications. [Android 15 listener and screen-share protection](https://developer.android.com/about/versions/15/behavior-changes-all#security), [Android 17 SMS protection](https://developer.android.com/about/versions/17/behavior-changes-all#sms-otp-all-apps).

After visibility is established, apply the [versioned publisher adapter contract](43-third-party-adapter-contract.md) before admission. A delivered notification is not proof of task identity, media-session equivalence or an executable action.
