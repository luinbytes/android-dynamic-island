# Android permissions and third-party access

[Specification index](../../REFERENCE_SPEC.md) · [onboarding and return-state proof](40-permission-onboarding.md)

## Permission contract and third-party app access

| Grant | Needed for | User flow and important distinction |
| --- | --- | --- |
| `SYSTEM_ALERT_WINDOW` | Drawing `TYPE_APPLICATION_OVERLAY` over ordinary app windows | Declare it, open `Settings.ACTION_MANAGE_OVERLAY_PERMISSION` when available, and recheck `Settings.canDrawOverlays()` after return. Android 11+ ignores an app package URI and opens the general app list, so the user selects this app there. It is a special access screen, not a normal runtime dialog. The overlay remains below status bar/IME and may be hidden by the system or another app's `HIDE_OVERLAY_WINDOWS`; keep input bounds small. [Onboarding contract](40-permission-onboarding.md), [Android 11 change](https://developer.android.com/about/versions/11/privacy/permissions), [window type](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY) |
| Notification listener access | Reading currently posted third-party notifications and, for a normal app, discovering cross-app active media sessions | Declare `NotificationListenerService` with its binding permission. Prefer the API 30+ app-detail Settings action with its component extra where available, otherwise the general listener Settings action. Check `NotificationManager.isNotificationListenerAccessGranted(component)`, then wait for `onListenerConnected()` and resnapshot; a grant is distinct from connection and from `POST_NOTIFICATIONS`. API 31+ filters and work-profile policy can still withhold events. [Onboarding contract](40-permission-onboarding.md), [listener visibility gate](27-notification-listener-visibility.md), [media sessions](https://developer.android.com/reference/android/media/session/MediaSessionManager) |
| `POST_NOTIFICATIONS` | Posting this app's own non-exempt notifications on Android 13+ | Runtime permission; it does **not** let the app read other apps' notifications. A foreground service can start without the grant but still must include its required service notification, whose visibility may be limited. [Notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission) |
| `POST_PROMOTED_NOTIFICATIONS` | Requesting promotion of this app's own qualifying Android Live Update | Manifest, `normal|appops` permission in the current API reference; on builds with promotion support it is **additional to** Android 13+ `POST_NOTIFICATIONS` notification posting access, not a replacement. It does not guarantee promotion or access to other apps' updates. For an app-owned ongoing task, check `NotificationManager.canPostPromotedNotifications()`, the channel and actual `FLAG_PROMOTED_ONGOING`, and offer `Settings.ACTION_MANAGE_APP_PROMOTED_NOTIFICATIONS` when the user wants to manage it. The system flag on another app's notification is read through enabled notification-listener access, not this permission. [Live Update requirements](https://developer.android.com/develop/ui/views/notifications/live-update), [permission](https://developer.android.com/reference/android/Manifest.permission#POST_PROMOTED_NOTIFICATIONS) |
| `ACCESS_NETWORK_STATE` | API 36+ tethering status callback | Declare this **normal** permission in the manifest for `TetheringManager.registerTetheringEventCallback()`. It is granted at install time, so do not present it as a runtime approval step. The callback is a status feed; this grant does not establish hotspot start/stop or client-count access. [TetheringManager](https://developer.android.com/reference/android/net/TetheringManager#registerTetheringEventCallback(java.util.concurrent.Executor,android.net.TetheringManager.TetheringEventCallback)), [permission level](https://developer.android.com/reference/android/Manifest.permission#ACCESS_NETWORK_STATE) |
| `DETECT_SCREEN_RECORDING` | API 35+ privacy behavior when **this app's activities** are visible in a screen recording | Normal manifest permission, needed for `WindowManager.addScreenRecordingCallback()` only if this optional app-local behavior is implemented. It does not reveal device-wide recording, recorder identity, microphone mode or stop control. Do not request it solely to build R16. [WindowManager callback](https://developer.android.com/reference/android/view/WindowManager#addScreenRecordingCallback(java.util.concurrent.Executor,java.util.function.Consumer)), [permission](https://developer.android.com/reference/android/Manifest.permission#DETECT_SCREEN_RECORDING), [recording ownership](25-screen-recording-ownership.md) |
| `READ_BASIC_PHONE_STATE` | Optional API 36+ satellite-modem-enabled callback on a device with satellite telephony | The public `SatelliteManager.registerStateChangeListener()` accepts this non-dangerous manifest grant, so `READ_PHONE_STATE` runtime access is not required solely for this callback. Enabled modem state does not prove a connection or grant emergency/roadside session control. Add the grant only if the selected-device satellite adapter is actually implemented. [SatelliteManager](https://developer.android.com/reference/android/telephony/satellite/SatelliteManager#registerStateChangeListener(java.util.concurrent.Executor,android.telephony.satellite.SatelliteStateChangeListener)), [permission](https://developer.android.com/reference/android/Manifest.permission#READ_BASIC_PHONE_STATE), [satellite entry](../features/26-satellite-entry.md) |
| Feature-specific runtime grants | Mobile call-state detection and Bluetooth headset state | Ask for `READ_PHONE_STATE` and `BLUETOOTH_CONNECT` only when enabling those adapters. These grants do not provide full call controls or universal earbud battery values. [Call state](https://developer.android.com/reference/android/telephony/TelephonyCallback.CallStateListener), [BluetoothHeadset](https://developer.android.com/reference/android/bluetooth/BluetoothHeadset) |

For a **locally installed APK** on Android 17, overlay and notification-listener access have an additional Restricted Settings gate before the user can grant them. Record installation source as part of permission proof; `Settings.canDrawOverlays()` or a listener Settings intent does not explain why a toggle is blocked. The user-controlled confirmation is in system App Info, and overlay and listener access must still be granted and verified separately afterward. This can affect a development APK even when the same manifest works through a trusted store. Follow the [onboarding and return-state contract](40-permission-onboarding.md) rather than treating restriction, denial and listener disconnection as one failure. [Android 17 compatibility definition](https://source.android.com/docs/compatibility/17/android-17-cdd), [Android Help](https://support.google.com/android/answer/12623953).

For an app-owned R22b control, declare the publisher's `TileService` with the `BIND_QUICK_SETTINGS_TILE` service permission and Quick Settings tile intent filter; this protects the service binding and does **not** grant the replica access to other apps' controls. The user must add the tile. Treat its click, the source task start, its notification post and any system-chip promotion as separate events. [Android Quick Settings tile guide](https://developer.android.com/develop/ui/views/quicksettings-tiles).

An **app-owned alarm publisher** for R10k has a separate permission audit. If its user-facing alarm needs an exact trigger on Android 12+, choose the appropriate `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM` route under the current platform eligibility rules and verify actual scheduling access. A full-screen alert path has its own `USE_FULL_SCREEN_INTENT` access and `NotificationManager.canUseFullScreenIntent()` check on supported releases; Android may show a heads-up notification instead. These permissions belong to a real alarm feature, not to the replica merely because it observes other apps' alarms. Preserve user notification settings and the system's actual lock/alert behavior. [Android alarm scheduling](https://developer.android.com/develop/background-work/services/alarms), [full-screen intent](https://developer.android.com/reference/android/app/NotificationManager#canUseFullScreenIntent()), [AlarmKit comparison](../features/33-alarmkit-alarm-lifecycle.md).

An **app-owned Push to Talk publisher** for R10l needs `RECORD_AUDIO` to capture speech and, when it actually uses a foreground microphone service, the `microphone` service type and corresponding foreground-service declaration. Android's while-in-use and background-start limits apply; notification-listener or overlay access does not grant cross-app microphone capture or a universal Talk command. The replica should not request these grants simply to display another publisher's posted channel status. [Microphone service requirements](https://developer.android.com/develop/background-work/services/fgs/service-types), [background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [PTT contract](../features/34-push-to-talk-channel.md).

An **app-owned VoIP publisher** for R10m declares `MANAGE_OWN_CALLS` when using Core-Telecom and registers its own calling capability with Telecom. It posts its required call notification and obtains any actual audio/video capture grants for its calling feature. These belong to the publisher implementing a real call, not to a replica observing a third-party `CallStyle` notification. `MANAGE_OWN_CALLS` does not make the replica a default dialer or grant another app's mute, hold, merge or hang-up authority. [Android Core-Telecom](https://developer.android.com/develop/connectivity/telecom/voip-app/telecom), [communication contract](../features/45-live-communication.md).

The planned `CameraManager.registerTorchCallback()` and `setTorchMode()` path does **not** call `openCamera()` and the public torch methods do not declare `CAMERA`; do not add a camera runtime prompt solely for torch status or on/off control. The selected device still needs a flash unit and may reject control while camera resources are busy. If an implementation later opens a camera device, audit that separate path and its `CAMERA` grant before adding it. [Torch API](https://developer.android.com/reference/android/hardware/camera2/CameraManager#setTorchMode(java.lang.String,boolean)), [camera-open API](https://developer.android.com/reference/android/hardware/camera2/CameraManager#openCamera(java.lang.String,android.hardware.camera2.CameraDevice.StateCallback,android.os.Handler)).

Do not request `SUBSCRIBE_TO_KEYGUARD_LOCKED_STATE` for an ordinary APK. Android reserves that lock-state callback permission for assistant-role or privileged/signature apps; public `KeyguardManager` state queries are a different contract. Listener access likewise does not override a publisher's `VISIBILITY_PRIVATE` or `VISIBILITY_SECRET` choice, a public redacted version, or the user's lock-screen settings. Follow the [lock-screen privacy proof gate](../verification/08-platform-proof-gates.md) before any third-party Island content appears outside the unlocked display. [KeyguardManager](https://developer.android.com/reference/android/app/KeyguardManager), [subscription permission](https://developer.android.com/reference/android/Manifest.permission#SUBSCRIBE_TO_KEYGUARD_LOCKED_STATE), [notification visibility](https://developer.android.com/reference/android/app/Notification#visibility).

Notification listener access can enable observation and transport control of another app's media session, but it is **not** a grant for `MediaRouter2` proxy routing of that app. The proxy API requires `MEDIA_CONTENT_CONTROL` (not for ordinary third-party apps) or `MEDIA_ROUTING_CONTROL` (reserved for the companion-watch role). Keep R9a's third-party route choice in the selected OS's actual output-owner flow or an explicit publisher integration; do not request those privileges in APK onboarding. [MediaRouter2 proxy contract](https://developer.android.com/reference/android/media/MediaRouter2#getInstance(android.content.Context,java.lang.String,java.util.concurrent.Executor,java.lang.Runnable)), [media permissions](https://developer.android.com/reference/android/Manifest.permission#MEDIA_ROUTING_CONTROL).

Third-party integration is **read/act on published contracts**, not arbitrary access to another app. A notification can provide text, progress, a tap destination, and optional `PendingIntent` actions; a media app can publish a `MediaSession`. The Island can surface only what is actually present and should invoke the publisher's action token rather than inventing a control. Missing/redacted fields, removed notifications, canceled actions, app/version changes, user-disabled notification channels, and listener revocation must all yield a truthful reduced or absent card. Android 15 redacts detected one-time codes from untrusted notification listeners. [Notification actions](https://developer.android.com/reference/android/app/Notification.Action), [Android 15 protection](https://developer.android.com/about/versions/15/behavior-changes-all).

An ongoing overlay service is not guaranteed to run forever merely because overlay access was granted. Choose a valid service type for real work, account for foreground-service notification rules, and test background starts and OEM process management. For apps targeting Android 15+, the `SYSTEM_ALERT_WINDOW` exemption for starting a foreground service from the background requires a **currently visible overlay** unless another exemption applies. [Foreground-service changes](https://developer.android.com/develop/background-work/services/fgs/changes).

An overlay grant also does **not** make audio or ringer setters reliable from the background. On Android 17, audio playback, audio-focus requests, and `AudioManager` volume/ringer changes require a visible Activity or a qualifying non-`SHORT_SERVICE` foreground service; API 37 targets face an additional while-in-use capability condition for a background foreground service, except the documented exact-alarm/`USAGE_ALARM` case. Volume and ringer setters can fail **silently**. This does not mean that every `MediaController.TransportControls` command is itself prohibited: the publisher receives and executes the command under its own audio lifecycle. For an app-owned ringer/media action, record caller visibility, service type/start context, target SDK, method result where provided, authoritative post-action state and native output. Never add a foreground service merely to draw a passive card. [Android 17 background audio hardening](https://developer.android.com/about/versions/17/changes/bg-audio).
