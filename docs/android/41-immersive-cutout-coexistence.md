# Immersive apps and physical cutout coexistence

[Specification index](../../REFERENCE_SPEC.md) · [R11b reference capture](../reference/02c-system-surfaces-capture.md) · [device qualification](18-device-qualification.md)

R11b covers a full-screen game or video, keyboard, Control Center/shade and Reachability as separate iPhone trials. Apple warns that the Island and home indicator may overlap game controls even when a game fills the screen; this does **not** establish whether an active Island is visible or touchable in every immersive state on iPhone 18 Pro Max/iOS 27. Capture the physical display externally while triggering one known Live Activity and one system alert in each state. Record app content, the Island, system bars, first edge-swipe result and return path, including the transition frames. [Apple fullscreen-game guidance](https://developer.apple.com/videos/play/wwdc2026/358/), [iOS 27 Island guide](https://support.apple.com/guide/iphone/view-live-activities-in-the-dynamic-island-iph28f50d10d/27/ios/27).

On Android, separate the **underlying app's layout** from the **replica window** and **SystemUI**. An app targeting SDK 35 on Android 15+ draws edge to edge under the system bars and display cutout; its non-floating cutout mode is effectively `ALWAYS`. That rule does not place a `TYPE_APPLICATION_OVERLAY` above the status bar or guarantee its placement over the physical camera. Immersive apps can hide system bars and request transient bars on an edge swipe. Treat the changing insets and transient-bar animation as distinct observations, not as a reason to pin the replica to a fixed screen `y` coordinate. [Android cutout guide](https://developer.android.com/develop/ui/views/layout/display-cutout), [window types](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY), [immersive mode](https://developer.android.com/develop/ui/views/layout/immersive).

## Target-build probe

Use a controlled edge-to-edge activity and a controlled immersive activity, then repeat with a named third-party game or video app. For each, test portrait and landscape with bars visible, bars hidden, transient bars revealed by swipe, notification shade open, keyboard open and the app returning from background. While one real source is active, log the replica window bounds, `WindowInsets` and `DisplayCutout` bounding rectangles, bar visibility, source ID, SystemUI chip/indicator positions and which window receives taps on each visible shape, transparent gap and top-edge swipe. Pair screen recording with external footage of the sensor; distinguish pixels drawn by the app, replica and SystemUI. Repeat with an app that requests overlay suppression if available. [Android insets](https://developer.android.com/develop/ui/compose/system/insets), [immersive mode](https://developer.android.com/develop/ui/views/layout/immersive), [overlay window](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY), [overlay suppression](https://developer.android.com/reference/android/Manifest.permission#HIDE_OVERLAY_WINDOWS).

The APK route passes a case only if the Island remains correctly placed when it is meant to be present, each visible control works, content behind the physical cutout stays usable, and the edge swipe still reveals the system controls. If a protected app suppresses the overlay, record the disappearance and source continuity; do not claim an always-visible Island. For a SystemUI route, trace the selected build's status-bar window, cutout decoration, immersive visibility controller and input owner before choosing a drawing seam. A successful APK screenshot cannot qualify that system route. Record separate visual and functional verdicts for every R11b case using the [comparison protocol](../verification/12-comparison-protocol.md).
