# Tap destination and action routing

[Specification index](../../REFERENCE_SPEC.md) · [interaction contract](../design/13-interaction-contract.md) · [Android events](06-android-events.md)

An Island tap has two independent outcomes: the Island's visible response and the **source destination or command that actually ran**. A matching opening animation with the wrong order, song, route or timer is an interaction failure. Preserve a stable source/session identity across compact, minimal, expanded, updated and reordered presentations.

## iPhone reference contract

Apple documents a default Live Activity tap that opens its containing app and passes an `NSUserActivity` whose `activityType` is `NSUserActivityTypeLiveActivity` when no URL is supplied. A `widgetURL(_:)` can instead open a matching scene from the Lock Screen, compact leading, compact trailing or minimal presentation; Apple says the **leading and trailing regions of the same compact activity should lead to the same screen**. The Dynamic Island configuration has its own `widgetURL(_:)` API. Expanded Live Activities can use `widgetURL(_:)` or individual `Link` routes and can contain intent-backed controls that perform work without opening the app; do not treat an action button as the card's ordinary tap destination. The actual hit targets, app scene, fallback and animation on iPhone 18 Pro Max/iOS 27 must be filmed. [Apple launch contract](https://developer.apple.com/documentation/ActivityKit/launching-your-app-from-a-live-activity), [default activity type](https://developer.apple.com/documentation/widgetkit/nsuseractivitytypeliveactivity), [interactive Live Activities](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities).

For the controlled R3a fixture, give two simultaneous activities from the **same app** distinct record IDs and URLs; each activity's compact leading and trailing regions use one matching record destination. Give each a separate expanded `Link` and one `LiveActivityIntent` button. Also run a version with no explicit URL and log whether the app receives `NSUserActivityTypeLiveActivity` through its actual scene/app callback. Tap compact leading, compact trailing, attached and detached minimal, expanded background, link and button separately. Record which app scene opens, whether it receives a URL or default user activity, whether a prior instance is reused, and whether an unlock prompt or failed destination interrupts the handoff. This proves the source-specific route instead of only proving that the publisher package launched.

## Android destination hierarchy

| Source | Candidate destination | Required proof |
| --- | --- | --- |
| App-owned activity | Explicit task/record route owned by the same app | The route identifies the current source, survives process recreation and opens the correct record after the Island reorders. Do not expose an old record after its source ends. |
| Inspected third-party notification | Its current `Notification.contentIntent`; individual `Notification.Action.actionIntent` only for the corresponding visible control | Keep the notification key and publisher identity bound to the token. Observe the actual destination and result on the named app version. Missing or canceled tokens mean no claimed tap/action parity. [Android Notification](https://developer.android.com/reference/android/app/Notification), [Notification.Action](https://developer.android.com/reference/android/app/Notification.Action) |
| Media session | `MediaController.getSessionActivity()` if the publisher supplies it; a notification destination only after proving it refers to the **same** media session | Do not merge a media session with a notification by package alone. Recheck the active token and session identity before dispatch. [Android MediaController](https://developer.android.com/reference/android/media/session/MediaController#getSessionActivity()) |
| System-owned surface, such as call, recording, assistant or privacy details | The selected OS's actual SystemUI/action owner | A replica must not invent a privileged destination or use an unrelated package launcher as proof of native system behavior. [AOSP SystemUI](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/README.md) |

A generic package launch is only a **documented fallback** if the publisher exposes no source-specific destination. Score it `approximate` when the iPhone opens a matching scene. Android 14 and later restrict background activity starts by senders of `PendingIntent`s, and Android 15 adds creator-side restrictions; the OS version, target SDK, sender visibility and publisher token all affect the result. Test a direct user tap from the actual APK overlay and from the selected SystemUI route separately, including denied launches and cancellation. Follow the platform's current opt-in rules where applicable; never report a successful route because `send()` returned without a visible correct destination. [Android activity-launch security](https://developer.android.com/guide/components/activities/secure-bal)

For one compact Android replica card, bind the leading and trailing hit regions to the **same current source destination** unless paired iPhone R3a footage proves an exception. A third-party notification's absent `contentIntent` does not imply Apple's default `NSUserActivity` handoff; the Android fallback may only open the publisher package and must retain an `approximate` interaction verdict when it misses the exact record. Expanded controls continue to use their own current action tokens.

## Dispatch and handoff rules

1. Resolve the **currently selected source ID** at touch-up; ensure it is still live and the hit target still belongs to that source. Do not dispatch a token captured before a reorder, removal, user switch, profile lock or access revocation.
2. Distinguish card tap, source-specific `Link` equivalent and command action. An Android notification action may update a task without opening UI; a media transport command is not a navigation token.
3. Dispatch at most once for one completed gesture. Cancel on `ACTION_CANCEL`, source loss or window teardown. A visual press is pending until the publisher or destination supplies a real result.
4. Observe the foreground package, activity/record shown and source state after dispatch. When a token is canceled, blocked, no longer resolvable or opens the wrong record, clear pending feedback and record the failure; do not animate a false success.
5. Keep lock and work-profile boundaries intact. If the platform requires authentication or the profile is unavailable, let its owner handle that transition and retest the final scene after unlock. Do not copy private notification text into an unlocked-looking Island as a workaround.

For a third-party notification card whose tap actually fires its **current** `contentIntent`, preserve Android's notification click semantics. If that notification has `FLAG_AUTO_CANCEL`, Android's listener API says to call `cancelNotification(key)` at that click; wait for the resulting removal callback and withdraw that notification-backed card without declaring an independently confirmed task ended. Do not cancel merely because the replica card appeared, expanded, was swiped for selection, or sent a separate action button. A failed or blocked destination must be recorded separately from the eventual notification state. `setNotificationsShown(keys)` marks notifications viewed and is only appropriate with sufficient evidence that the user explicitly viewed them; passive Island display or an incoming callback is not that evidence. On the selected build, compare native shade seen/dismissal state after passive display, explicit expansion, content tap and action-button tap. [Android listener click and seen contracts](https://developer.android.com/reference/android/service/notification/NotificationListenerService#cancelNotification(java.lang.String)).

## R3a evidence record

Record iPhone activity ID, configured URL/default route, tapped region, actual app scene, app-process state and lock state. Record Android `(user/profile, package, notification key or media token, publisher session ID when supplied)`, current destination-token source, tap coordinates, selected source before/after, send result, visible destination record, task state and any launch denial. Pair the two runs in the [comparison protocol](../verification/12-comparison-protocol.md). Overall R3a stays `unverified` until both real devices prove the correct destination and the other required layers.
