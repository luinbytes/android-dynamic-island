# Native capture execution plan

[Specification index](../../REFERENCE_SPEC.md) · [78-state matrix](02-state-capture.md) · [fixture contracts](11-reference-fixtures.md) · [paired comparison](../verification/12-comparison-protocol.md)

This is the **capture order**, not a claim that a session has run. The provisional iPhone reference is iPhone 18 Pro Max on iOS 27.0.1, Apple's latest listed version on 2026-09-29; recheck at acquisition and record the exact installed build. The Android comparison uses one separately qualified model/build. There is no native iPhone reference package, selected Android build or attached Android device yet; every listed parity verdict remains `unverified`. [Apple security releases](https://support.apple.com/en-us/100100).

## Prepare once, before recording

1. Recheck the latest iOS release and record the iPhone's exact installed version **and build**, display settings, language/region, accessibility and privacy settings, and the installed versions of each source app. Record the Android model, build fingerprint, API level and display settings when selected. Keep those settings fixed within a comparison run, then change one variable at a time. If the iPhone updates, start a new reference package and compare overlapping rows before carrying a prior verdict forward.
2. Set up a fixed external camera with the whole phone, display edges and sensor region visible; lock exposure, focus and white balance for contour/color comparisons. Record actual frame rate and file dimensions. Register the display corners and record alignment residuals before measuring pixels. If the camera cannot resolve a timing difference, report an interval rather than inferring a subframe curve. Use screen recording as a secondary source for digital content: Apple's recording control itself occupies the Island. [Apple screen-recording guide](https://support.apple.com/guide/iphone/take-a-screen-recording-iph52f6e1987/27/ios/27), [comparison protocol](../verification/12-comparison-protocol.md).
3. Use nonpersonal fixture labels and a visible trigger marker linked to the publisher's event log. Preserve the full raw clips, including idle lead-in and settled tail, and repeat each transition at least three times. Log **absence** as a result only after a reproducible trigger and an adequately long recorded observation window; an unavailable source or permission is `unverified`, not a negative Island result.
4. For ActivityKit trials, prepare the [controlled iPhone publisher](11-reference-fixtures.md#iphone-activitykit-publisher), distinct publisher identities for concurrency, and source IDs that can be read from logs. Prepare a separate Android publisher package for notification/media trials. Do not replace first-party system actions or named third-party apps with lookalike fixtures.

## Evidence bundle and closure

Use a stable file stem such as `C02_R5_run03_iphone_external` and the [evidence manifest](../verification/18-evidence-manifest.md) to link each clip to its trigger log, raw file hash, actual frame dimensions/rate, registration transform, R-state measurement sheet and reviewer verdict. Keep raw footage immutable; redact personal fields only in review copies. Record the companion Android source event, native chip/shade/lock presentation, replica frame and action result under the same R ID when a target build exists. [Measurement sheet](02-state-capture.md#measurement-sheet-for-each-captured-state), [Android source map](../verification/10-state-to-android-map.md).

Close a capture row only after the expected trigger was confirmed, at least three repeat runs agree within recorded uncertainty, relevant negative/interference cases are present, and each required visual, motion, interaction, source and system-coexistence layer has evidence. A source citation or fixture log alone cannot close a visual layer. The overall verdict uses the weakest required layer from the [comparison protocol](../verification/12-comparison-protocol.md); missing device footage remains `unverified`.
