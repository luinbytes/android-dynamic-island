# Android platform proof gates

[Specification index](../../REFERENCE_SPEC.md)

## Further platform findings and proof gates

**Top edge and camera cutout.** `LAYOUT_IN_DISPLAY_CUTOUT_MODE_ALWAYS` allows a window to extend into display-cutout areas, and `WindowInsets.getDisplayCutout()`/`DisplayCutout` provide geometry. Neither rule raises an application overlay above the status bar. The target-phone experiment must log the overlay's actual window rectangle, display-cutout bounds, status-bar insets, and touch hit region in portrait and landscape; capture the screen and externally photograph the camera area. A “drawn at y=0” log is insufficient if SystemUI masks the pixels or intercepts touch. Also test immersive/full-screen content, shade pull-down, keyboard, lock screen, and another app that suppresses overlays. Follow the [R11b immersive/cutout probe](../android/41-immersive-cutout-coexistence.md) for edge-to-edge and transient-bar cases. [Cutout layout mode](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#LAYOUT_IN_DISPLAY_CUTOUT_MODE_ALWAYS), [overlay Z-order](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY), [cutout guide](https://developer.android.com/develop/ui/views/layout/display-cutout).

**Reachability and one-handed mode.** Apple's Reachability lowers screen content, while Android's one-handed mode can bring the top half down; neither guide states that an APK overlay follows the transformed app content or that either Island stays in a specific place. In R11b, film the physical camera boundary and the rendered Island together before, during and after each mode, then tap the visible Island and the original top-edge location. Record which surface owns the tap, whether the shade still opens, and whether source selection survives. Keep Apple’s old iOS 16 Island/Reachability bug note as historical context, not an iOS 27 expected result. [Apple Reachability](https://support.apple.com/en-mt/guide/iphone/iph145eba8e9/ios), [Android one-handed mode](https://support.google.com/accessibility/android/answer/12652418), [iOS 16 updates](https://support.apple.com/en-us/101566).

**SystemUI geometry ownership.** AOSP separates status-bar window management from content insets and screen decorations. On the chosen build, record which component owns the status-bar window bounds, reserved text/icon space, cutout fill and privacy dot; then change only the necessary owner(s) for the Island. Recheck rotation, multi-activity width, clock/connectivity icons, the promoted Live Update chip and shade touch region. A black pill that looks correct in one screenshot but covers a native chip or duplicates the cutout mask is not a native-feel pass. These AOSP classes are investigation pointers, not an OEM integration recipe. [AOSP status-bar window controller](https://android.googlesource.com/platform/frameworks/base/+/615ad7a7880964ed28ccfdd6eebaa84342911b1e/packages/SystemUI/src/com/android/systemui/statusbar/window/StatusBarWindowController.java), [content insets provider](https://android.googlesource.com/platform/frameworks/base/+/e5bca37fb55dcf49be7fbe95b01c0e5b02c03997/packages/SystemUI/src/com/android/systemui/statusbar/phone/StatusBarContentInsetsProvider.kt), [ScreenDecorations](https://android.googlesource.com/platform/frameworks/base/+/1685e6b9319b/packages/SystemUI/src/com/android/systemui/ScreenDecorations.java).

**App-to-Island handoff.** For R1a, record the real app-window transition and Island frames together when leaving and returning to the publisher app. The APK prototype can animate on its own notification/media event timing, but cannot assume it shares the window transition's frame clock or source element. On a selected SystemUI build, inspect the WM Shell/SystemUI transition boundary and determine whether a synchronized handoff is possible for an app-owned publisher, an ordinary third-party notification publisher and a media publisher separately. If an arbitrary source view is inaccessible, record a measured approximation rather than claiming a shared-element morph. [Apple design session](https://developer.apple.com/videos/play/wwdc2023/10194/), [AOSP WM Shell overview](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/libs/WindowManager/Shell/src/com/android/wm/shell/docs/overview.md).

**Privacy and recording ownership.** Android's camera/microphone/location indicator and its usage dialog are a paired system contract. AOSP says SystemUI listens for relevant app-ops and `PermissionController` supplies the tapped usage details; an APK overlay must leave these system indicators and their touch path unobstructed. In a selected SystemUI build, coordinate the Island renderer with that existing indicator owner instead of drawing an independent, potentially stale dot. For screen recording, distinguish the OS's own recording chip/control from another app's projection session; inspect the selected build's recording owner and preserve its stop confirmation and error behavior. API 35's recording callback reports whether the registering app's **activities** are visible in a recording; it does not confer global recording ownership on an overlay. Follow the [R16 recording proof](../android/25-screen-recording-ownership.md). Neither source establishes that Apple's green/orange dots occupy the Island itself. [AOSP privacy indicators](https://source.android.com/docs/core/permissions/privacy-indicators), [AOSP screen-recording chip change](https://android.googlesource.com/platform/frameworks/base/+/72b3afc154c2987b4e7f56f5b0866b39f737e12a), [Apple status indicators](https://support.apple.com/en-us/108331).

For an Android 17 handheld R21 trial, start precise location from a foreground non-system fixture app and verify the required visible location indicator, its tap/details path and clearance around each Island shape. Test approximate-only and background location separately; the Android 17 compatibility rule cited here does not promise the same indicator for those conditions. Pair the actual native result with iPhone R21 footage rather than mapping either platform's indicator color by assumption. [Android 17 compatibility definition](https://source.android.com/docs/compatibility/17/android-17-cdd).

**Notification discovery and freshness.** Android supports listener filter types for ongoing, alerting, conversations, and silent notifications. Since the desired activities are often ongoing, do not copy the API example that disables the ongoing type; explicitly check the selected listener filters on the target device. On connection, snapshot active notifications; process posted, removed, and ranking updates; on disconnection, invalidate the snapshot until reconnected. The posted notification's `EXTRA_PROGRESS`/`EXTRA_PROGRESS_MAX` may provide progress, while `FLAG_ONGOING_EVENT` says it represents an ongoing event, but neither proves precise time remaining or a meaningful Island action. [Listener filters and callbacks](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [notification fields](https://developer.android.com/reference/android/app/Notification).

**Notification seen and click state.** A passive overlay frame or listener callback is not a user-view event. `setNotificationsShown(keys)` may be called only when the user has actually viewed the keyed notifications with sufficient confidence; log any use and compare native shade state. For a tapped notification `contentIntent` carrying `FLAG_AUTO_CANCEL`, follow the listener's `cancelNotification(key)` click contract and observe the removal callback. Expansion, source switching and distinct action buttons are separate interactions. Test both flag states and a continuing publisher task so cancellation cannot masquerade as task completion. [Listener seen/click methods](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [destination contract](../android/19-destination-routing.md).

**Promoted Live Updates.** On Android API 36+, the system sets `Notification.FLAG_PROMOTED_ONGOING` when a notification is actually promoted; a notification listener can read that flag. Treat it as a strong candidate signal for an ongoing third-party activity, then inspect the publisher's actual fields and actions. The posting app cannot set the flag directly, and `hasPromotableCharacteristics()` alone does not guarantee promotion. For our **own** qualifying, user-initiated ongoing task, Android's native Live Update can be a separate optional system surface; it requires the promotion request and `POST_PROMOTED_NOTIFICATIONS` declaration **in addition to** notification posting access, an allowed style, ongoing flag/title and a channel above `IMPORTANCE_MIN`; user/OEM policy still controls promotion. Check `NotificationManager.canPostPromotedNotifications()` for the app-owned publisher and distinguish promotion eligibility, user setting, actual flagged state and visible chip in diagnostics. Do not post a promoted notification solely to advertise the replica. The full owner and coexistence checks are in the [Android surface ownership contract](../android/15-android-surface-ownership.md). [Notification promoted flag](https://developer.android.com/reference/android/app/Notification#FLAG_PROMOTED_ONGOING), [Live Update rules](https://developer.android.com/develop/ui/views/notifications/live-update).

**Chip and demotion coexistence.** A promoted Live Update has a separate system-owned chip, promoted shade card and Lock Screen card. The chip always has an icon, may show short text or a countdown, and has a documented 96 dp maximum width; it is not an arbitrary-size Island canvas. Users can demote or dismiss a Live Update. On the selected Android build, capture the system chip and replica together, then demote, dismiss, update and end the publisher's task. Record whether `FLAG_PROMOTED_ONGOING` changes, whether the notification remains visible, and which renderer owns tap and shade behavior at each step. A SystemUI implementation must make one explicit decision about chip replacement or coexistence; an APK cannot assume it can suppress that chip. For app-owned updates, do not repost an unwanted Live Update after dismissal. [Android Live Update behavior](https://developer.android.com/develop/ui/views/notifications/live-update), [Android Live Update design](https://developer.android.com/design/ui/mobile/guides/home-screen/live-updates).

**Alert attention and StandBy.** R6/R6a must distinguish an ordinary publisher state update from an actual alert. The replica may render a measured expansion from a real source event, but it cannot infer that another app requested sound or screen wake just because notification text changed. Android notification channels and user settings govern alert interruption; an app-owned urgent notification may use the appropriate channel, while a copied third-party sound or a generic full-screen intent would be misleading. On Android 14+, default full-screen-intent access is limited to apps whose core function is calling or alarms, with a separate user setting; do not use it as a generic Island alert mechanism. For R11a, `DreamService` offers a user-selected charging screensaver surface, but its launch, touch behavior and lock transition require target-device proof. [Android notification importance](https://developer.android.com/reference/android/app/NotificationManager#IMPORTANCE_HIGH), [full-screen intent rules](https://developer.android.com/about/versions/14/behavior-changes-14), [DreamService](https://developer.android.com/reference/android/service/dreams/DreamService).

**Media precision and tap-through.** `MediaController.Callback` can deliver session state/metadata changes. `PlaybackState` supplies position, playback speed, last update time, and supported actions, so the presentation can interpolate a progress indicator from a real timestamp and stop it when paused; missing or stale state should display no fabricated progress. A session may expose a `getSessionActivity()` destination. Notification `contentIntent` and actions are publisher-supplied `PendingIntent`s, but background activity-launch rules can prevent some launches; verify tap-through from a visible overlay on each target Android version instead of assuming every token opens an app. [MediaController](https://developer.android.com/reference/android/media/session/MediaController), [PlaybackState](https://developer.android.com/reference/android/media/session/PlaybackState), [Android 15 activity-launch changes](https://developer.android.com/about/versions/15/behavior-changes-15).

**Interactive and remote publisher contract.** For R18, an Android notification action is a publisher-supplied `PendingIntent`, not a generic equivalent of iOS `LiveActivityIntent`. Display an in-Island control only when the exact publisher and version expose that action; observe its resulting notification/state before claiming success, and hide it if the token disappears or fails. For R20, inspect whether the Android publisher exposes a `MediaSession` representing the remote device, the advertised transport actions and any route/device identity; do not label a local Android session as remote just because the iPhone reference uses a remote session. These are per-publisher parity tests. [Android notification actions](https://developer.android.com/reference/android/app/Notification.Action), [Android media sessions](https://developer.android.com/reference/android/media/session/MediaSessionManager), [Apple remote Now Playing](https://developer.apple.com/videos/play/wwdc2026/312/).

**Accessibility of custom rendering.** A single canvas or custom View does not automatically expose each visual Island control to TalkBack. Give compact and expanded actions separate accessibility nodes with source, state, label, and enabled action; provide keyboard and switch-access actions where applicable. `ExploreByTouchHelper` or an equivalent virtual hierarchy can expose distinct interactive regions without changing the visual contour. For R19, pair Apple's documented focused-Island swipe-up option navigation and double-tap with the selected Android build's actual TalkBack action menu; log the spoken label, selected source, action result and focus after the source disappears. Android `AccessibilityNodeInfo.AccessibilityAction` supports custom labeled actions and standard expand/collapse actions, but it does not supply Apple's Explore Screen or Ask About Screen service. Inspect focus order and spoken updates when an activity appears, changes priority or disappears. Android recommends touch targets of at least 48 dp; if that target cannot coexist with the measured iPhone silhouette and nearby system gestures, record the visual/accessibility tradeoff rather than silently shrinking the target. [Apple VoiceOver guide](https://support.apple.com/en-ie/guide/iphone/iph37e6b3844/27/ios/27), [Android action API](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo.AccessibilityAction), [accessible custom views](https://developer.android.com/guide/topics/ui/accessibility/views/custom-views), [touch targets](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views).

**Assistant gesture ownership.** Apple now uses an Island swipe-down path for Siri AI when available. On Android, determine whether the selected build exposes the active assistant through its assistant role or an assist intent, and whether an Island-origin swipe can reach it without stealing the notification shade's downward gesture. Record idle, active-card and expanded-card starts, failed/unavailable assistant cases, return to the prior card, keyboard focus and TalkBack access. `ACTION_ASSIST` is a general Android assist action; it does not provide Apple's Siri AI features or guarantee that a top-edge overlay can invoke the device assistant under background-activity and gesture rules. [Apple Siri AI entry](https://www.apple.com/newsroom/2026/09/siri-ai-a-profoundly-more-capable-and-personal-assistant-is-here/), [Android assistant role](https://developer.android.com/reference/android/app/role/RoleManager#ROLE_ASSISTANT), [Android assist intent](https://developer.android.com/reference/android/content/Intent#ACTION_ASSIST).

**Biometric trust boundary.** For R25, compare the iPhone's real unlock and app-authentication appearance with Android keyguard and a genuine `BiometricPrompt` from an app under test. Record success, failed match, cancellation and credential fallback, plus what happens to any Island card. The prompt is a system-provided authentication UI and its callback belongs to the requesting app. A normal overlay must yield to it; a SystemUI implementation can coordinate surrounding visuals only after tracing the target build's biometric owner. Never use a replicated Face ID glyph or animation as evidence that Android authenticated a user, and do not intercept or replace another app's prompt. [Apple iPhone 18 Pro announcement](https://www.apple.com/newsroom/2026/09/apple-debuts-iphone-18-pro-and-iphone-18-pro-max/), [Android BiometricPrompt](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt).

**Lock-screen and capture privacy.** A listener receiving a notification does not thereby gain authority to show its full contents on the keyguard, AOD or a shared screen. Android notifications distinguish `VISIBILITY_PUBLIC`, `VISIBILITY_PRIVATE` (optionally with a `publicVersion`) and `VISIBILITY_SECRET`; an active notification's `Ranking.getLockscreenVisibilityOverride()` can report a user or device-policy override, while channel/system settings and profile state further affect effective output. For the APK prototype, query `KeyguardManager.isKeyguardLocked()` and `isDeviceLocked()` at each presentation decision and on lifecycle refresh, but do not claim a public lock-state subscription: `addDeviceLockedStateListener()` and `addKeyguardLockedStateListener()` require `SUBSCRIBE_TO_KEYGUARD_LOCKED_STATE`, which is reserved for assistant-role or privileged/signature apps. If the effective visibility policy or screen-sharing state is unknown, withhold third-party details rather than re-render raw listener fields. A selected SystemUI build must reuse or reproduce its effective notification privacy decision, including work-profile and user-switch boundaries; raw `Notification.visibility` **or one ranking override** alone does not prove what the current user may see. `FLAG_SECURE` is a possible APK capture-protection tool to test, but it also changes screenshot/recording behavior and cannot replace the lock-screen policy. Run public/private/secret publishers with public versions, hide-sensitive-content setting, locked versus unlocked, AOD, profile lock, screen recording/sharing and return from each state. Record publisher visibility, public version, ranking override, replica and native notification output, including whether any text or action leaks before authentication. [Android notification visibility](https://developer.android.com/reference/android/app/Notification#visibility), [ranking visibility override](https://developer.android.com/reference/android/service/notification/NotificationListenerService.Ranking#getLockscreenVisibilityOverride()), [lock-screen guidance](https://developer.android.com/develop/ui/compose/notifications/create-notification#lock-screen), [KeyguardManager](https://developer.android.com/reference/android/app/KeyguardManager), [restricted subscription permission](https://developer.android.com/reference/android/Manifest.permission#SUBSCRIBE_TO_KEYGUARD_LOCKED_STATE), [secure window flag](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#FLAG_SECURE).

TypeSafe evaluations on 2026-09-28 answered two different scopes. With a **user-installable APK without root** assumed, Choice favored public-API adapters and a bounded overlay over Accessibility inference or OS modification (1.0); Noul estimated 0.04 for claiming exact system integration from that normal app. With the user's full native-integration goal and no installability constraint, Choice favored the two-route plan—overlay design prototype plus target-specific SystemUI investigation (1.0)—and Noul again estimated 0.04 for overlay-only full parity. These are judgment signals, not platform proof, permission or numeric acceptance criteria. The linked contracts and device results decide actual capability.

Cross-app media session discovery requires either `MEDIA_CONTENT_CONTROL` or an **enabled notification listener** passed to `MediaSessionManager`; use the latter route for a normal app and handle lost/revoked listener access. Wait for `onListenerConnected()` before querying active notifications, and rebind after disconnection. Android 15 also protects sensitive notification content such as one-time codes, so adapters must work with missing or redacted fields. [MediaSessionManager](https://developer.android.com/reference/android/media/session/MediaSessionManager), [NotificationListenerService lifecycle](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [Android 15 notification protections](https://developer.android.com/about/versions/15/behavior-changes-all).

Android Live Updates are a **system-owned status chip and notification** for eligible ongoing, user-initiated, time-sensitive tasks. Promotion depends on notification characteristics, user settings, and potentially OEM criteria; it does not let a third-party app draw the iPhone shape into SystemUI. Treat this as a separate optional Android-native companion surface, not the rendering mechanism for visual parity. [Android Live Updates](https://developer.android.com/develop/ui/views/notifications/live-update).

Phone-call controls require a separate product decision. Android's `InCallService` contract belongs to an app that takes the **default dialer** role and implements full incoming/outgoing call UI; it is not a lightweight permission for an Island overlay. Until that role change is deliberately in scope, treat system calls as notification-dependent and do not claim reliable call control. [Android InCallService](https://developer.android.com/reference/android/telecom/InCallService).

Other apps can suppress non-system overlay windows on sensitive screens using `HIDE_OVERLAY_WINDOWS`; the Island must tolerate disappearing there. Android 12+ also blocks unsafe pass-through touches under untrusted overlays. These platform rules set a hard limit on always-visible parity. [Overlay suppression permission](https://developer.android.com/reference/android/Manifest.permission#HIDE_OVERLAY_WINDOWS), [untrusted touch behavior](https://developer.android.com/about/versions/12/behavior-changes-all).

The overlay must leave touch outside the visible Island unobstructed and yield to security-sensitive system UI. Android 12+ restricts touches passed through untrusted overlays; use a small, bounded window and verify actual hit testing. Obtain cutout bounds and system insets from `WindowInsets`/`DisplayCutout` where exposed, rather than guessing the hole position. The status bar may still occlude a third-party overlay, so a device-level top-edge feasibility spike is required before claiming sensor alignment. [Android window touch rules](https://developer.android.com/reference/android/view/WindowManager.LayoutParams), [window insets](https://developer.android.com/reference/android/view/WindowInsets), [display cutouts](https://developer.android.com/develop/ui/views/layout/display-cutout).

For disconnected R4/R5/R5b shapes, test the transparent gaps **inside** any enclosing overlay rectangle separately from touches outside the rectangle. `FLAG_NOT_TOUCH_MODAL` only describes outside-window dispatch, while `FLAG_NOT_TOUCHABLE` disables the whole window and can trigger Android's untrusted-touch block for pass-through events. Record actual recipient and Logcat evidence during shape morphs, not just screenshots. Follow the [interaction gap-touch gate](../design/13-interaction-contract.md). [Window flags](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#FLAG_NOT_TOUCH_MODAL), [Android 12 touch behavior](https://developer.android.com/about/versions/12/behavior-changes-all).
