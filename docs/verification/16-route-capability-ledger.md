# Android route capability ledger

[Specification index](../../REFERENCE_SPEC.md) · [state-to-Android map](10-state-to-android-map.md) · [surface ownership](../android/15-android-surface-ownership.md)

This ledger records **source-backed capability ceilings**, not observed 1:1 results. Every R-row's overall verdict remains `unverified`: there is no native iPhone 18 Pro Max/iOS 27 capture, selected Android build or paired runtime comparison. A public Android API may prove that one signal is available; it cannot prove the iPhone contour, Android placement, action result or native feel. `APK ceiling` describes a normal user-installed app with ordinary user-granted access. `System route` is a candidate in a selected, buildable SystemUI/OEM implementation, not permission automatically acquired by the APK.

## Verdict rule

For each R-row, record **five separate fields**: visual, motion, interaction, source/action and system coexistence. Record the implementation route and publisher version. An API ceiling can be `direct`, `publisher-dependent`, `role/system-owned` or `unavailable to ordinary APK`; these are **capability labels**, not a `matched` verdict. The row's overall verdict remains `unverified` until the paired [comparison protocol](12-comparison-protocol.md) has native iPhone and target Android evidence. Once measured, use `approximate` for a difference and `unsupported` for a demonstrated missing capability on the chosen route; do not turn a source-backed limitation for one layer into an unsupported judgment for the entire R-row without inspecting the other layers and route. A SystemUI candidate remains `unverified` until its actual build path and runtime behavior are shown.
