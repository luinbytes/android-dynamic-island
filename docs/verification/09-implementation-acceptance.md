# Implementation and acceptance

[Specification index](../../REFERENCE_SPEC.md)

## Proposed implementation

1. **Reference package:** prepare the controlled [ActivityKit and Android publisher fixtures](../reference/11-reference-fixtures.md), then follow the [native capture execution plan](../reference/12-capture-execution-plan.md): C00–C04 establish R0–R8 and cross-cutting surfaces first; subsequent sessions cover all other rows, including R22a's real APNs start/update/end path and R22d's [App Clip no-full-app start](../features/35-app-clip-live-activity.md). Create a frame and measurement ledger with uncertainty. Capture first-party controls on the real phone. Until native footage exists, use Apple documentation to build provisional layouts only.
2. **Device and OS gate:** complete the [device qualification record](../android/18-device-qualification.md) for one Android phone/build: measure the physical cutout and system-bar layout, probe actual APK overlay behavior, and inspect SystemUI source or a supported OEM integration path and device recovery options. If no viable OS path exists, record that platform-layer 1:1 is unavailable on that target rather than silently treating an APK as equivalent.
3. **Design engine:** implement the [source and presentation state machine](../design/14-state-machine.md), event-priority arbiter, device geometry profiles and one renderer specification for contour, content, gesture hit regions and transitions. Measure iPhone thresholds and curves before declaring them final. Keep event adapters independent of the renderer.
4. **Installable prototype:** build a Kotlin app with a bounded, cutout-aware overlay, [explicit overlay/listener onboarding and return-state checks](../android/40-permission-onboarding.md), adapter toggles, diagnostics and stop control. Prove actual top-edge placement, status-bar occlusion, rotation and hit testing on the target phone. Choose any foreground service according to the actual work and target API; observing another app's media is not itself `mediaPlayback`. [Foreground-service changes](https://developer.android.com/develop/background-work/services/fgs/changes), [service-type requirements](https://developer.android.com/develop/background-work/services/fgs/service-types).
5. **Live signals:** integrate media sessions first, then direct battery/ringer/torch signals and an app-owned timer. Add headset, call-state and one notification publisher at a time with their actual permissions, actions and teardown. Verify [listener visibility and filters](../android/27-notification-listener-visibility.md), then apply the [notification admission contract](../android/20-notification-admission.md) and R26 negative cases before turning a listener post into an Island source. Treat R10g as surface discovery and R10h as a documented Action-button control case whose actual iOS 27 appearance, duration and alternate entry routes still need capture; a real Android ringer signal does not prove that button interaction. Add three visible activities only after R5 arbitration is captured; keep a fourth accepted source in the store and validate its overflow/promotion behavior against R5b before claiming capacity parity. Probe R5d hide/restore against activity switching before defining Android gesture thresholds.
6. **System integration when the selected OS supports it:** move the renderer and event arbiter into the inspected SystemUI surface. Use the [surface ownership contract](../android/15-android-surface-ownership.md) to coordinate status icons, privacy indicators, notification shade, promoted Live Updates, keyguard and AOD through that build's real owners. Keep publisher data bounded to its contracts. Disable the prototype overlay when the system implementation is active; verify boot, restart and update behavior.
7. **Paired real-device tuning:** compare iPhone and Android captures for geometry, typography, optical alignment, motion and touch response. Record font/icon source and license through the [typography and icon contract](../design/17-typography-icons.md) before selecting Android assets. Exercise media, the R9a route offer/transfer, timer, charging, ringer, torch, headset, calls and selected publishers; then test R10j [Action-button control feedback](../features/32-action-button-control-feedback.md), R10k [AlarmKit lifecycle](../features/33-alarmkit-alarm-lifecycle.md), R15a authorization/frequent-update changes, R18a [interactive toggle](../features/31-interactive-toggle.md) feedback/commit/lock paths, R22b Control Center starts and R22c Action-button shortcut starts, listener revocation, source termination, rotation, immersive apps, shade, lock and AOD. Check lock/AOD and screen-sharing content against public/private/secret notification visibility, public redacted versions and user/profile settings; a raw listener field must not bypass native redaction. Test R24/R24a against the selected Android assistant, Search provider and shade gestures, including unavailable-provider paths. On API 36+ also exercise Live Update requested, promoted, user-demoted, dismissed and ended states plus [short-critical-text chip precedence](../android/15-android-surface-ownership.md); record when the native chip appears, changes or disappears and check that the replica does not create conflicting tap or shade behavior. On API 37+, test the [MetricStyle, semantic-style and action-hint publisher cases](../android/15-android-surface-ownership.md#android-17-publisher-styling-and-chip-content) against the actual chip/card and listener payload, then invoke each real action in unlocked and locked states. Record visible and action results separately.
8. **Capability release gate:** mark an adapter `matched` only after target-phone and publisher-version checks of real source, action, teardown and permission changes. Mark system-layer behavior `approximate`, `unsupported` or `unverified` when the chosen route cannot prove parity.

## Acceptance record

For R10l [Push to Talk](../features/34-push-to-talk-channel.md), first determine whether the target iOS build presents its joined-channel indicator in the Island or elsewhere. If it does, pair channel join, transmit/receive, call interruption, service loss, leave and locked operation with a named Android publisher and verify its real audio/privacy result. An Android microphone dot or phone-call card is not PTT source proof.

For each R-state, follow the [paired comparison protocol](12-comparison-protocol.md): keep an iPhone reference and Android capture/recording, measurement sheet, frozen tolerances, implementation route (`APK` or selected `SystemUI` build), separate visual/motion/interaction/source/system results and an overall verdict of `matched`, `approximate`, `unsupported`, or `unverified`. Use the [route capability ledger](16-route-capability-ledger.md) to keep documented API ceilings distinct from the overall verdict. A state is `matched` only after visual comparison **and** the real interaction pass on the target Android phone. For R6/R6a, compare screen wake, sound and return state as well as shape; for R11/R11a, compare sensitive-content redaction and the entire charging/StandBy transition, including [Night Mode tint, display-off and tap expansion](../features/36-standby-night-privacy.md), not just one frame; for R16/R16a, prove screen recording and Local Capture as separate source/control paths; for R22/R23, prove pending-start and each transient teardown path rather than treating both as ordinary activity updates; for R22d, score the no-full-app entry separately from the later installed-app task and destination; for R25, require a real platform biometric result and report any visual match separately. Native-feel acceptance also requires unbroken shade gestures, status/privacy indicators, lock/AOD handoff, TalkBack actions, correct source teardown, and no duplicate system chip/card. Source code, preview renders and synthetic events establish progress but cannot prove device parity. Document every Android-specific system-layer difference rather than hiding it in a screenshot.

## Current gaps

- No iPhone 18 Pro Max/iOS 27 native capture is available here. Apple's launch video establishes an example of the two- and three-activity composition, but does not publish the redesigned Island's native contour, widths, or motion curves.
- A [stock Pixel 11 Pro XL on stable Android 17](../android/04-pixel-android17-baseline.md) is the provisional primary Android profile; no physical Pixel unit or exact build is selected. A connected Samsung SM-S906E running Android 16 was verified through ADB on 2026-09-29 as a separate prototype test bed. Pixel-specific overlay placement and runtime behavior remain unverified.
- No target Android OS build, editable SystemUI source, signing path or safe recovery route has been selected. A native SystemUI integration is therefore an architecture path to validate, not an implemented or confirmed option on a particular phone.
- The repository now has a buildable public-API APK on `feature/android-app-scaffold`. [Samsung physical evidence](13-samsung-prototype-evidence.md) covers the bounded portrait/landscape overlay, screen-sleep removal, temporary overlay and listener grant/revocation, multi-timer countdown/overflow/selection, process-restart restore, exact and delayed inexact completion, reboot rescheduling, timer destination routing, screenshot protection, notification Pause/Resume/Clear actions, opt-in charging/torch sources and a controlled Chrome MediaSession with dashboard and expanded-pill Play/Pause dispatch. A [Samsung Clock listener probe](14-samsung-clock-admission.md) confirmed that Clock reuses and reshuffles notification keys across concurrent timers, so its external timer source remains withheld. These are prototype results, not iPhone visual matching or Pixel/Android 17 qualification. The completion channel is silent; locked keyguard/AOD privacy, other media publishers, system-chip coexistence and an accepted third-party notification adapter have not passed physical acceptance. Inspect the current PR head and evidence before treating any later stage as accepted.
