# Action-button control feedback in the Island

[Specification index](../../REFERENCE_SPEC.md) · [capture matrix](../reference/02-state-capture.md) · [Action-button activity start](29-action-button-start.md)

Apple's Controls guidance says a user-assigned control on an iPhone Action button displays its **symbol and optional value** in the Dynamic Island when the person presses and holds the button. A control can be a button or a two-state toggle. The guide shows Silent Mode as an example, recommends on/off symbols and animations for toggles, and says an action that takes time can animate while it runs. Tint, hint text, redaction and authentication are publisher-controlled aspects of this control route. This is an Island state **even if no Live Activity is started**. The guidance is general, so its iPhone 18 Pro Max/iOS 27 exact shape, press threshold, timing and result still need native capture. [Apple Controls HIG](https://developer.apple.com/design/human-interface-guidelines/controls).

## R10j reference run

Use a harmless, controlled on/off action (for example a test light state) and a separate delayed button action. Assign each to the Action button in turn. Record the assigned control ID, on/off value, symbol pair, tint, configured hint/redaction and source command/result. Film from first press through hold, release, pending work, success, rejection and return to the prior Island activity. Capture idle, one active Live Activity and three active Live Activities, plus Lock Screen and user-canceled authentication. Compare a short press, an unassigned button and the system Silent Mode control as controls; do not assume every assignment produces the same pill.

Measure the symbol and value bounds, text and color, contour and keyline, entrance/exit frames, haptic or sound, overlap with status/privacy indicators, activity displacement and restoration, VoiceOver label, and whether a failed command visually rolls back. Record what the underlying publisher **actually did** separately from what the Island displayed. For security-sensitive controls, record whether the value is redacted before unlock and whether canceling authentication prevents the action.

## Android integration boundary

A normal Android publisher can expose an app shortcut or its own in-app control and can publish the resulting task/value through an explicit integration or notification. `ShortcutManager` does not assign a physical device button. A notification listener also cannot infer a hardware-button press merely from a later notification update. The replica may show a corresponding **app-owned** command/result only when it knows the source and current value; it must not claim to reproduce Apple's system Action-button feedback for arbitrary apps. [Android ShortcutManager](https://developer.android.com/reference/android/content/pm/ShortcutManager), [notification listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

On the selected Android model/build, inspect any documented OEM hardware-button mapping and its actual callback or launched destination. If a supported mapping invokes the controlled publisher, log press time, publisher invocation, real state change, listener arrival and first replica frame separately. A selected SystemUI integration must coordinate that device's input owner, status-bar surface and keyguard redaction; an APK overlay cannot assume it receives the system button gesture or owns lock presentation. If the target has no usable button route, score hardware input `unsupported` for that route while recording any separate visual approximation honestly. The overall R10j verdict stays `unverified` until paired native captures exist.
