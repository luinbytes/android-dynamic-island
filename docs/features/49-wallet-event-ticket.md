# Wallet event-ticket activity and pass suggestion

[Specification index](../../REFERENCE_SPEC.md) · [R10q capture](../reference/02b-system-activities-capture.md) · [Wallet flight contrast](48-wallet-flight-activity.md)

Apple's Wallet HIG, updated for iOS 27, says the system can start a Live Activity for **certain pass types, including event tickets**, and illustrates an event-ticket Live Activity on the Lock Screen. Separately, pass relevance metadata can make a pass appear as a **Lock Screen suggestion** at a matching date or location. A suggested pass, an issuer update notification and a system-started Live Activity are distinct outcomes. Apple does not say that every event ticket qualifies, that the suggested-pass metadata always starts an activity, or what an eligible ticket looks like in the iPhone 18 Pro Max Island. Treat current Island presence as a native measurement candidate. [Apple Wallet HIG](https://developer.apple.com/design/human-interface-guidelines/wallet/), [pass relevance](https://developer.apple.com/documentation/walletpasses/showing-a-pass-on-the-lock-screen).

## R10q native capture

Use a legitimate test ticket from a cooperating issuer, recording pass style, event ID/date, relevance dates/locations, issuer app/version, Live Activities settings and iOS build. Compare an eligible poster or semantic ticket with a simple legacy ticket when available. Capture before the relevance interval, when its date matches, near the venue with permission, at event start, after entry/scan and after event end. For each stage record four separate surfaces: Wallet pass, Lock Screen **suggestion**, Lock Screen **Live Activity**, and unlocked **Island presence or absence**. If an Island activity exists, measure compact/minimal/expanded content, onset, alert, tap/hold destination, coexistence with a publisher's own event activity, and end; keep pass redemption/barcode and source task outcomes under their real owners. Test an issuer pass update separately from the system activity. Do not infer an activity from a suggested pass or a screenshot of a different event; capture the actual pass and its system behavior on iOS 27. [Apple Wallet HIG](https://developer.apple.com/design/human-interface-guidelines/wallet/), [pass relevance](https://developer.apple.com/documentation/walletpasses/showing-a-pass-on-the-lock-screen).

## Android integration boundary

Google Wallet documents an upcoming-event notification three hours before an event and conditional issuer field-update notifications. The Wallet app owns its pass and redemption UI. These notifications are inspectable only if actually delivered to the enabled listener, and they do not document an ongoing event Live Update or a replica-owned entry credential. Capture notification key, fields, `contentIntent`, action list, grouping, lock visibility, expiry and the pass opened for a controlled test ticket. If an issuer app separately publishes an ongoing event task, preserve its identity and do not merge it with Google Wallet's pass reminder without a verified common owner/task contract. The replica must not display a barcode, claim admission or replace NFC/QR redemption from notification text. [Google Wallet event notifications](https://developers.google.com/wallet/tickets/events/use-cases/trigger-push-notifications), [Google Wallet event tickets](https://developers.google.com/wallet/tickets/events), [Android listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

R10q stays `unverified` for current Island presence and every parity layer until the native iPhone and chosen Android runs satisfy the [comparison protocol](../verification/12-comparison-protocol.md). A measured suggestion-only case is a negative Island result, not an excuse to invent a card.
