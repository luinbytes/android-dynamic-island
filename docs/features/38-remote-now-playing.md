# Local and remote Now Playing sessions

[Specification index](../../REFERENCE_SPEC.md) · [capture states](../reference/02-state-capture.md) · [Android events](../android/06-android-events.md)

Apple's iOS 27 Now Playing framework publishes local playback and publisher-controlled **remote** playback to system surfaces including the Dynamic Island. The remote example uses a stable session ID, content and playback snapshot, a list of remote devices with stable IDs and capabilities, APNs-driven extension updates, and publisher command handlers that forward actions to the remote device. This establishes a source and action path, **not** the iPhone 18 Island's exact pixels or a guarantee that every media app adopts the framework. A remote playback session differs from Music's transient HomePod route offer (R9a): one describes the current ongoing player; the other offers a possible transfer. [Apple WWDC26 Now Playing](https://developer.apple.com/videos/play/wwdc2026/312/).

Apple describes Media Sharing Extensions as a way for a publisher to offer its supported routes through the **system device picker**; it names Control Center as a place where the selection is reflected. That is a route-selection contract, not evidence of a new Island card or of route controls in every expanded media view. In R9a/R20 capture, record the actual Island affordance, picker owner and post-selection playback state separately. [Apple WWDC26 Now Playing](https://developer.apple.com/videos/play/wwdc2026/312/).

## Multiple local sessions and system selection

The preliminary Now Playing API documents multiple **local sessions in one app**. Each `MediaSessionRepresentable` supplies a stable ID, content, playback snapshot and supported commands. `requestToBecomeApplicationPrimary()` changes which local session represents that app; `requestToBecomeSystemPrimary()` also requests the active system session and has **no effect when called from the background**. The publisher releases a completed session by dropping its session reference. Apple says not to mix this framework with `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter` for local playback because the result is undefined. These are publisher contracts, not a published iPhone Island priority algorithm. R20a captures whether and how each accepted primary change reaches the Island and how commands bind to the selected session. Recheck these preliminary APIs against the final iOS 27 SDK before building a fixture. [Apple Now Playing framework](https://developer.apple.com/documentation/nowplaying), [publishing local sessions](https://developer.apple.com/documentation/nowplaying/publishing-media-sessions).

## R9/R20 reference capture

Use a controlled publisher with one local session and one remote session backed by a test speaker/server. Keep stable, distinct session and device IDs. Start local playback, publish remote playback, switch between them, pause/resume/skip, change remote volume, delay one remote push update, disconnect the speaker, and end each session. Record Island and Lock Screen presence, source selection, content/artwork, local-versus-remote label and device name, available actions, command request/result, first visible frame and stale/exit behavior. Log server send, APNs/extension receipt and device acknowledgment separately; a tap or push delivery alone does not prove the speaker changed state. Repeat with another media app active and with the publisher app foreground/background. [Apple WWDC26 Now Playing](https://developer.apple.com/videos/play/wwdc2026/312/).

## Android integration boundary

An enabled notification listener can obtain active `MediaController`s from `MediaSessionManager`, subject to the publisher's actual session and permissions. `MediaController.getPlaybackInfo().getPlaybackType()` distinguishes local from remote **volume handling**; `PLAYBACK_TYPE_REMOTE` is a useful publisher-declared signal, but it does not by itself name the speaker, prove a separate server-backed session, or supply a route-transfer command. Inspect the live session token, metadata, playback state, advertised transport actions, playback info, and any named route/device contract. A `VolumeProvider` can handle remote volume for an app-owned session; cross-app volume or transport actions must be sent only when the actual controller supports them, then checked against the publisher/device result. Do not infer a remote session from Bluetooth connection, a cast icon, or a notification alone. [Android MediaController.PlaybackInfo](https://developer.android.com/reference/android/media/session/MediaController.PlaybackInfo), [MediaSessionManager](https://developer.android.com/reference/android/media/session/MediaSessionManager), [VolumeProvider](https://developer.android.com/reference/android/media/VolumeProvider).

Android 17 can silently suppress a **publisher's** background playback or volume operation if its audio lifecycle lacks a visible Activity or qualifying foreground service; API 37 targets have a further while-in-use service condition. This rule does not establish that the replica's `MediaController.TransportControls` dispatch failed. Treat dispatch, publisher callback, updated playback state and audible/device result as separate observations. A control can show success only after the real source confirms it; otherwise show the pending/failure outcome and keep native media controls available. The cooperating Android media fixture must exercise foreground, screen-off, valid service and invalid-service states on the selected build. [Android 17 background audio hardening](https://developer.android.com/about/versions/17/changes/bg-audio).

Keep local and remote session identities separate, then deduplicate each with its own notification only when the publisher contract proves they represent the same playback. If device identity or an action result is unavailable to an ordinary APK, retain the truthful media information and record that layer as publisher-dependent or `unsupported` for the selected route. R9/R20 overall remain `unverified` until native iPhone and paired Android playback, control and visual runs pass the [comparison protocol](../verification/12-comparison-protocol.md).

For R20a, inspect two distinct Android media-session tokens from one cooperating publisher, their active playback states, advertised actions, and the native system-selected player before and after a publisher-controlled switch. An enabled listener can observe active sessions; on API 37, `getActiveSessionsForPackage(packageName, notificationListener)` additionally returns that package's tokens in priority order. That order is an Android signal, not Apple's application/system-primary state and not a guarantee that the native media chip chose the same controller. Test API 36 or lower with the existing active-controller list and native output inspection. Do not synthesize two Island cards for one selected player or let a stale token retain working controls after release. [Android MediaSessionManager](https://developer.android.com/reference/android/media/session/MediaSessionManager), [Android PlaybackState](https://developer.android.com/reference/android/media/session/PlaybackState).

For route selection, use the publisher's own media-routing contract or hand off to the OS-owned output switcher when available. Android documents that `MediaRouter2.showSystemOutputSwitcher()` expects a foreground, visible context and can return `false` for a background caller. A background Island overlay must therefore test the real foreground handoff and return path on the selected build; it cannot treat the output-switcher call as a guaranteed inline Island action. [Android MediaRouter2](https://developer.android.com/reference/android/media/MediaRouter2).
