# One Live Activity with rotating event content

[Specification index](../../REFERENCE_SPEC.md) · [R5c capture](../reference/02-state-capture.md) · [state machine](../design/14-state-machine.md)

Apple's Live Activities design guidance recommends using **one Live Activity** with a dynamic layout that rotates through several events, rather than creating separate activities for each event. Its example cycles through sports scores, substitutions and fouls across matches. This is publisher-authored content inside one ActivityKit identity; it does not establish a new system arbitration rule, automatic carousel timing or extra Island slots. [Apple Live Activities HIG](https://developer.apple.com/design/human-interface-guidelines/live-activities).

## R5c native capture

Build one controlled ActivityKit source with a stable activity ID and a known sequence of event IDs/types. Update its content from score to substitution to foul and back, first at a relaxed cadence, then with rapid consecutive updates; vary compact/minimal/expanded content and one change in contour width. Keep a second publisher's activity active for part of the sequence. Record which updates actually reach the Island, element/shape transition and duration, whether the selected source and slot stay stable, tap destination and expanded controls after each event, and whether any event is skipped or coalesced. Compare an explicit two-activity fixture with the same visible text so one-card content rotation cannot be mistaken for the system's multi-activity swipe. Apple recommends this design pattern but does not publish the target phone's exact timing or content transitions.

## Android identity and update contract

An app-owned publisher can update one Android notification using the same `(tag, id)`; `NotificationManager.notify()` replaces its current information. That preserves one notification identity, but does not supply ActivityKit's layout regions, animation or event IDs automatically. The publisher should expose a stable task/session ID and current event ID/type when the replica needs an event-specific destination or action. Android documentation also warns that notification updates can be rate limited, so first visible/last visible content and actual delivery must be measured on the selected build. [NotificationManager](https://developer.android.com/reference/android/app/NotificationManager#notify(java.lang.String,int,android.app.Notification)), [notification update guidance](https://developer.android.com/develop/ui/compose/notifications/create-notification).

For a third-party publisher, observe only the fields and updates delivered by its notification or explicit contract. Do not split each text change into a new source, spend another Island slot, or infer an event-specific action from a generic notification tap. Preserve the task identity while replacing the current event payload; expire a former event's action token when that payload changes. If the publisher does not expose event IDs, record the visible text change as a notification update with **unknown event identity**. Test notification removal and listener reconnect while the content rotates. [Android listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService), [destination routing](../android/19-destination-routing.md).

R5c's source/action, visual, motion, interaction and system-coexistence verdicts remain `unverified` until iPhone 18 Pro Max footage and a named Android publisher/build are paired. One Android notification update is an integration candidate, not 1:1 evidence.
