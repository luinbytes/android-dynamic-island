# Wallet boarding-pass flight activity

[Specification index](../../REFERENCE_SPEC.md) · [R10p capture](../reference/02b-system-activities-capture.md) · [Android notification admission](../android/20-notification-admission.md)

Beginning in iOS 26, an airline's **semantic boarding pass** can let Wallet track a flight through Apple's flight service and provide a Wallet-owned Live Activity. The pass supplies structured airline/flight/departure data; Wallet can update flight status, gate and delay information without the airline updating every pass. The Live Activity can be shared through Messages. Apple also documents `associatedStoreIdentifiers` as a way to suppress Wallet's Live Activity when an associated app supplies its own. This is a different owner from a flight tracker such as Flighty, a legacy boarding pass, an ordinary Wallet change message, and a Lock Screen pass suggestion. Apple's cited WWDC25 and Wallet documentation establish the framework route, but do not publish exact iPhone 18 Pro Max/iOS 27 Island geometry or the timing of every phase. [Apple Wallet WWDC25](https://developer.apple.com/videos/play/wwdc2025/202/), [semantic boarding pass](https://developer.apple.com/documentation/walletpasses/creating-an-airline-boarding-pass-using-semantic-tags), [Wallet HIG](https://developer.apple.com/design/human-interface-guidelines/wallet/).

## R10p native capture

Use a legitimate, nonpersonal pass for a real scheduled flight with airline authorization and a region supported by Apple's flight service. Record pass style, Wallet/airline app version, flight identifier, departure date, whether the airline app is associated for suppression, and the exact iOS build; redact passenger and barcode data. Capture before adding the pass, after add, predeparture, gate/terminal or delay change, boarding, airborne/offline, arrival and end. Record Wallet pass, notification, Lock Screen and Island **presence or absence** for each phase; if Island appears, measure compact/minimal/expanded content, source identity, alert motion, tap destination, coexistence with a separate flight-tracker activity and final teardown. Run a legacy-pass control and, when an airline test setup permits it, an associated-app suppression control. Share the flight tracker with a second test account and record the recipient's source and destination separately; sharing is not proof that the recipient has the original boarding pass or personal details. Do not invent flight changes or use an arbitrary fabricated pass as proof of Apple's live flight service. [Apple Wallet WWDC25](https://developer.apple.com/videos/play/wwdc2025/202/), [semantic boarding pass](https://developer.apple.com/documentation/walletpasses/creating-an-airline-boarding-pass-using-semantic-tags).

## Android publisher and Wallet boundary

Google Wallet supports real-time updates **on supported boarding passes** and can post an upcoming-flight notification and conditional gate, boarding-time or departure-time change notifications. Its developer documentation describes Google Flights integration and flight-status notifications. These are native Wallet pass/notification surfaces, not a documented universal third-party flight-session API or guaranteed Android Live Update chip. Inspect the selected Google Wallet build's delivered notification key, fields, `contentIntent`, actions, grouping, lock visibility and actual pass result for one real test pass. Do not turn a three-hour reminder, one gate-change alert or the presence of a saved pass into a continuous Island flight tracker without an explicit ongoing publisher contract. Keep the airline, Google Wallet and any separate flight-tracker app as distinct source identities; deduplicate only when their actual source contract shows the same task and owner. A cooperating airline app can publish its own ongoing task and destination, but cannot grant the replica Google Wallet's private pass data. [Google Wallet flight pass help](https://support.google.com/wallet/answer/12059256?hl=en), [Google Wallet boarding-pass notifications](https://developers.google.com/wallet/tickets/boarding-passes/use-cases/trigger-push-notifications), [Google Wallet pass updates](https://developers.google.com/wallet/tickets/boarding-passes/use-cases/updates), [Android listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

R10p remains `unverified` for current Island presence, presentation, actions and Android parity. Separate source/action and system-surface verdicts under the [comparison protocol](../verification/12-comparison-protocol.md); a Google Wallet alert cannot be scored as a matched ongoing flight activity merely because it opens the right pass.
