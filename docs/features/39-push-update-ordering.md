# Remote update ordering, priority and stale content

[Specification index](../../REFERENCE_SPEC.md) · [capture states](../reference/02-state-capture.md) · [state machine](../design/14-state-machine.md)

Apple's ActivityKit push payload has an `event` (`start`, `update`, `end`), `timestamp`, publisher `content-state`, optional `stale-date`, and optional alert. Apple says the timestamp helps the system display the most recent push update, and a push arriving **after the Live Activity ended** is ignored. APNs `apns-priority: 10` is the immediate, budgeted path (and default when omitted); priority `5` is lower priority and does not count toward that budget. The frequent-push setting permits a higher update budget when the publisher opts in and the user allows it. These are transport/source facts, not a published iPhone 18 Island frame cadence. [Apple ActivityKit push guidance](https://developer.apple.com/documentation/ActivityKit/starting-and-updating-live-activities-with-activitykit-push-notifications), [ActivityKit authorization](https://developer.apple.com/documentation/activitykit/activityauthorizationinfo).

Apple also caps combined Live Activity static/dynamic data at 4 KB, including data in ActivityKit pushes. R22a must distinguish an APNs send/response from an accepted ActivityKit revision and a rendered Island frame when a boundary payload is attempted. Do not infer that an oversized push is displayed, or map Apple's limit onto FCM without a separate Android publisher contract. [Apple ActivityKit constraints](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities).

## iPhone R22a/R15a/R5c/R12 proof

Use one controlled ActivityKit ID and server event IDs. Send ordered updates, then deliberately deliver an older-timestamp update after a newer one; end the activity, then deliver another update. Run `apns-priority` 5 and 10 in separate trials with logged send, APNs result, device receipt/activity state and first visible Island frame. Repeat with frequent pushes enabled/disabled and a stale date that passes during a network gap. Record whether old/post-end content was accepted, whether the activity became stale, what the Island actually rendered, and whether an alert expanded it; do not call a missing frame throttling without proving transport delivery. Avoid rapid artificial pushes that conflate APNs budget, device delivery and animation coalescing. The 2023 WWDC description of a setting change ending activities is historical; measure iOS 27 behavior rather than adopting it as a rule. [Apple ActivityKit push guidance](https://developer.apple.com/documentation/ActivityKit/starting-and-updating-live-activities-with-activitykit-push-notifications), [Apple WWDC23 push session](https://developer.apple.com/videos/play/wwdc2023/10185/).

## Android integration boundary

For a cooperating Android publisher, use authenticated FCM data with a stable source ID plus publisher-assigned monotonic revision or server timestamp. FCM does **not** guarantee delivery order; a collapsible message can replace an older pending one, so the publisher must reconcile against authoritative task state before publishing its notification or replica event. Normal priority can be delayed in Doze; high priority attempts prompt delivery but can be deprioritized if it repeatedly fails to produce user-visible content. These priority names and budgets are **not** APNs 5/10 equivalents. A notification listener sees only the resulting published notification, not the other app's FCM payload, ordering decision or hidden task state. For app-owned sources, reject stale revisions and any update after a confirmed end unless a new source identity is created; expire controls immediately and report the actual published state. [FCM collapsible messages](https://firebase.google.com/docs/cloud-messaging/customize-messages/collapsible-message-types), [FCM Android priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority), [Android notification listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

Compare one app-owned Android publisher with the iPhone fixture, then test a named third-party publisher from its actual notification fields. Keep five timestamps distinct: server event, transport send, device/publisher receipt, notification publication/listener callback, and first visible frame. Report transport/source fidelity and visual/motion fidelity separately. R22a and related rows remain `unverified` without both native runs; an Android task that reaches the same final text after dropping intermediate states may still differ in motion or alerts.
