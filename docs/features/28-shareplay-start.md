# SharePlay start around the Island

[Specification index](../../REFERENCE_SPEC.md) · [R28 capture](../reference/02-state-capture.md) · [Android event contracts](../android/06-android-events.md)

Apple's SharePlay design guidance shows a shared TV activity during FaceTime with a short start message **around the Dynamic Island**, a participant image badged with the app icon, and content text. This is visual evidence of a SharePlay start presentation in Apple's guide, not proof of the exact iPhone 18 Pro Max/iOS 27 pixels, that it is a persistent Live Activity, or that every SharePlay app receives the same treatment. SharePlay can start from a FaceTime call or Messages conversation; participants may need to launch or install the sharing app. [Apple SharePlay HIG](https://developer.apple.com/design/human-interface-guidelines/shareplay).

## R28 native capture

With two test Apple Accounts and a supported, nonpersonal SharePlay activity, record both initiator and recipient phones. Start sharing during FaceTime; separately start from Messages if supported by the selected publisher. Film the Island externally before invitation, during participant acceptance, at session start, while a call and shared media coexist, when a second activity arrives, and when one participant leaves or sharing ends. Record participant/app badge, text, contour and duration, compact versus expanded behavior, tap/hold destination, whether a Live Activity exists independently, PiP and Lock Screen transitions, and the final state. Log source-app/version and group-session phase; avoid capturing personal contact names. A generic media session or call alone is the negative control. If the current target phone does not display the guide's start message, record that as a measured version/publisher difference rather than copying the older artwork.

## Android integration boundary

An Android `MediaSession` exposes a publisher's playback state and transport controls; `TelecomManager` supports call integration. Neither contract by itself supplies the group-activity invitation, participant identity, synchronized session phase or SharePlay-specific start message. A named Android publisher could expose a verified group-session event and action directly to the replica, or a listener-visible notification may carry limited invitation or task data. Admit only the fields and actions actually published, and keep the call UI, media controls, notification and native chip with their owners. Do not infer “sharing started” from simultaneous call plus playback. [MediaSession](https://developer.android.com/reference/android/media/session/MediaSession), [TelecomManager](https://developer.android.com/reference/android/telecom/TelecomManager), [notification listener](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

The target Android proof must name the call app, shared-media app and versions; log a publisher's invitation/start/end contract, actual notification or media-session fields, participant/action availability, deep-link destination, and duplicate native surfaces. If no contract exists, score the shared-session data and action layer as `unavailable` for that publisher; the visual, motion and coexistence layers remain `unverified` until paired footage. [Admission rule](../android/20-notification-admission.md), [destination routing](../android/19-destination-routing.md).
